第 6 章 — パスワードハッシュとセッション (Bearer Token)

Ch.5 で残した 3 つの大きな抜けを、 ここで全部直します:

  • ❌ パスワードを平文で DB に保存している (= DB が漏洩したら全員のパスがバレる)
  • ❌ ログインしても、 その後どのリクエストが「ログイン中の誰」 かサーバが知らない
  • ❌ /api/me と /api/logout がハードコードのまま

4 スパイラルで:

  1. パスワードを pbkdf2 でハッシュ化
  2. sessions テーブル + Bearer Token を発行
  3. フロントが Token を保管 → Authorization ヘッダで送る
  4. /api/me と /api/logout をセッション対応に

6.1 そもそも「ハッシュ」 と「暗号」 は別物

📚 コラム: ハッシュ vs 暗号

初めて触れる人は混同しがちなので、 違いをハッキリ:

ハッシュ関数(共通鍵) 暗号
方向一方向 (戻せない)双方向 (鍵があれば戻せる)
例SHA-256, MD5, bcrypt, pbkdf2AES, ChaCha20
用途パスワード保管、 改ざん検知、 ID生成通信の秘密保持、 ファイル暗号化
同じ入力 → 出力常に同じ (= 決定的)初期値で変えるのが普通

パスワードの保管に必要なのは「漏洩しても元のパスを復元できない」性質。 だから暗号 (戻せる) ではなくハッシュ (戻せない) を使います。 ログイン時は「入力されたパスを同じハッシュ関数に通して、 保存値と比較」 で照合。

SHA-256 を 1 回かけるだけでは弱い

ハッシュ関数は同じ入力なら同じ出力なので、 事前計算した変換表が攻撃に使えます (レインボーテーブル攻撃)。 「password = abc123 → ハッシュ = X」 を表で持っておけば、 漏れたハッシュ X からパスワードを一瞬で逆引きできてしまう。

対策が 2 つ:

  • ソルト (salt): ユーザーごとにランダムな byte 列を作って、 ハッシュ計算に混ぜる → 同じパスでもユーザーごとに違うハッシュになる → 事前計算表が使えない
  • 反復回数: 同じハッシュを何万回も繰り返す → 1 回の計算が遅くなる → 総当たり攻撃の手間が桁違いに増える

これを束ねたのが pbkdf2 (Password-Based Key Derivation Function 2)。 Python 標準ライブラリ hashlib に最初から入っています。

Spiral 1 — pbkdf2 でパスワードをハッシュ化

hash_password と verify_password の 2 関数を作って、 Ch.5 の register / login に組み込みます。

📒 セル 6-A — パスワードハッシュの 2 関数 
import base64, hashlib, hmac, os

# pbkdf2 のパラメータ
_ALGO = "sha256"
_ITER = 200_000     # 200,000 回繰り返す (= 1 回の計算で 0.1 秒前後かかる)
_SALT_BYTES = 16    # ソルトの長さ
_DK_BYTES = 32      # ハッシュ出力の長さ

def hash_password(password: str) -> str:
    """パスワード文字列をハッシュ化して、 DB に保存する文字列を返す。

    保存形式: pbkdf2_sha256$200000$$
    """
    salt = os.urandom(_SALT_BYTES)                      # ユーザーごとにランダム
    dk = hashlib.pbkdf2_hmac(_ALGO, password.encode("utf-8"),
                             salt, _ITER, dklen=_DK_BYTES)
    return "$".join([
        f"pbkdf2_{_ALGO}",
        str(_ITER),
        base64.b64encode(salt).decode(),
        base64.b64encode(dk).decode(),
    ])


def verify_password(password: str, stored: str) -> bool:
    """入力パスワードと保存ハッシュを照合する。"""
    try:
        algo, iter_s, salt_b64, hash_b64 = stored.split("$")
    except ValueError:
        return False
    if not algo.startswith("pbkdf2_"):
        return False
    digest_name = algo.split("_", 1)[1]
    iters = int(iter_s)
    salt = base64.b64decode(salt_b64)
    expected = base64.b64decode(hash_b64)
    actual = hashlib.pbkdf2_hmac(digest_name, password.encode("utf-8"),
                                 salt, iters, dklen=len(expected))
    # タイミング攻撃に強い比較 (詳しくは後のコラム)
    return hmac.compare_digest(actual, expected)


# 動作確認
h1 = hash_password("hunter2")
h2 = hash_password("hunter2")
print("h1:", h1[:60], "...")
print("h2:", h2[:60], "...")
print("h1 == h2 ?", h1 == h2)                    # ソルトが違うので False
print("verify hunter2 :", verify_password("hunter2", h1))   # True
print("verify HUNTER2 :", verify_password("HUNTER2", h1))   # False
✅ 期待される出力 
h1: pbkdf2_sha256$200000$a/L+8yxRz... ...
h2: pbkdf2_sha256$200000$xK7Q9XP+a... ...
h1 == h2 ? False
verify hunter2 : True
verify HUNTER2 : False
📚 コラム: hmac.compare_digest って何が違う?

普通の == 比較は、 文字列を頭から見比べて違いが出た瞬間に return します。 だから「最初の 1 byte が合っているか」 と「最後まで全て合っているか」 で応答時間に差が出る。

攻撃者が大量のリクエストを投げて応答時間を測れば、 「正解に近い byte」 を当てていける (タイミング攻撃)。 これを防ぐのが hmac.compare_digest = 文字列の長さを揃えて、 どんな入力でも常に同じ時間で結果を返す比較関数。

パスワード照合や HMAC のシグネチャ検証には必ずこれを使う、 が業界の常識です。

register / login を pbkdf2 化

Ch.5 で書いた 2 ハンドラの「平文保存」 部分だけ書き換えます。

📒 セル 6-B — register / login にハッシュを組み込む 
@route("POST", "/api/register")
def register(h):
    body = h._read_json()
    name = (body.get("name") or "").strip()
    password = body.get("password") or ""
    display_name = (body.get("display_name") or "").strip() or name
    if len(name) < 3 or len(name) > 32:
        raise bad_request("name は 3〜32 文字")
    if len(password) < 6:
        raise bad_request("password は 6 文字以上")

    pass_hash = hash_password(password)             # ← ここで Ch.5 の平文保存からハッシュ化に

    with get_conn() as conn:
        cur = conn.execute("SELECT 1 FROM users WHERE name = ?", (name,))
        if cur.fetchone():
            raise bad_request("その name は既に使われています")
        cur = conn.execute(
            """
            INSERT INTO users (name, pass_hash, display_name)
            VALUES (?, ?, ?)
            RETURNING id, name, display_name
            """,
            (name, pass_hash, display_name),
        )
        row = dict(cur.fetchone())
    row["coins"] = 1000
    h._json(200, {"user": row})


@route("POST", "/api/login")
def login(h):
    body = h._read_json()
    name = (body.get("name") or "").strip()
    password = body.get("password") or ""

    with get_conn() as conn:
        cur = conn.execute(
            "SELECT id, name, display_name, pass_hash FROM users WHERE name = ?",
            (name,),
        )
        row = cur.fetchone()

    # ← 平文比較から verify_password に
    if row is None or not verify_password(password, row["pass_hash"]):
        raise AppError(401, "name か password が違います")

    user = {"id": row["id"], "name": row["name"],
            "display_name": row["display_name"], "coins": 1000}
    h._json(200, {"user": user})

print("✅ register/login がハッシュ化版に")

  • 新しく alice / secret123 で登録 → %%sql SELECT pass_hash FROM users; → pbkdf2_sha256$200000$... という長文字列に
  • 同じ secret123 でログイン → ✅ 通る
  • WRONGPASS でログイン → 401
  • 2 ユーザーを同じパスワードで登録 → 各 pass_hash を SELECT すると違う値 (= ソルトが効いている)

6.2 ログイン後の状態管理 — どうやって覚える?

ログイン成功は確認できた。 でも次のリクエスト (例: ガチャを引く) が来たとき、 サーバはどうやって「これは alice の操作」 と判別するのか?

📚 コラム: HTTP はステートレス

HTTP の重要な性質: 1 つの往復ごとに完結していて、 サーバはリクエスト間の関係を覚えない。 ステートレス (stateless = 状態を持たない) と呼びます。

だから「あなたは alice」 という情報は、毎回のリクエストに何かを添えて送る必要があります。 この「何か」 = セッショントークン。

添える方法は主に 2 通り:

  1. Cookie: ブラウザが自動で添えてくれる。 サーバが Set-Cookie ヘッダで発行 → ブラウザが保存 → 次のリクエストで自動的に Cookie ヘッダで送り返す
  2. Authorization ヘッダ (Bearer Token): クライアント側でトークンを保管して、 毎回 Authorization: Bearer <token> ヘッダを明示的に付ける

ブラウザのフォーム送信では Cookie が自然。 一方 REST API + SPA や、 モバイルアプリ、 サーバ間連携では Bearer Token が定番。 どちらも長所短所ありますが、 本教材は Colab + クロスオリジン環境で Cookie 設定が地雷だらけなので、 業界でも広く使われるBearer Token 方式を採用します。

Spiral 2 — sessions テーブル + トークン発行

ログイン成功時に、 サーバは:

  1. ランダムな十分長い文字列 (= トークン) を生成
  2. その文字列を「これは user_id=X のトークン」 として sessions テーブルに保存
  3. レスポンスの JSON に "token": "..." を含めて返す

クライアントは受け取ったトークンを保管して、 以後のリクエストで Authorization ヘッダに乗せて送る。

sessions テーブルを作る

📒 セル 6-C — sessions テーブル 
%%sql
CREATE TABLE IF NOT EXISTS sessions (
    token      TEXT    PRIMARY KEY,                                    -- ランダムな文字列
    user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE, -- 誰のトークンか
    created_at TEXT    NOT NULL DEFAULT (datetime('now')),
    expires_at TEXT    NOT NULL                                         -- いつまで有効か
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);

トークン操作の 3 関数

📒 セル 6-D — セッション操作 
import secrets
from datetime import datetime, timedelta, timezone

SESSION_TTL = timedelta(days=7)        # 1 週間で失効

def new_session_token() -> str:
    """十分に長い暗号学的乱数 (256bit) を URL-safe な文字列に。"""
    return secrets.token_urlsafe(32)

def create_session(conn, user_id: int):
    """sessions に行を追加して (token, expires_at) を返す。"""
    token = new_session_token()
    expires = (datetime.now(timezone.utc) + SESSION_TTL).strftime("%Y-%m-%d %H:%M:%S")
    conn.execute(
        "INSERT INTO sessions (token, user_id, expires_at) VALUES (?, ?, ?)",
        (token, user_id, expires),
    )
    return token, expires

def lookup_session(conn, token: str):
    """token から user 情報を引く。 期限切れ / 不在は None。"""
    if not token:
        return None
    cur = conn.execute(
        """
        SELECT u.id, u.name, u.display_name, s.expires_at
          FROM sessions s
          JOIN users    u ON u.id = s.user_id
         WHERE s.token = ?
        """,
        (token,),
    )
    row = cur.fetchone()
    if row is None:
        return None
    # 期限切れチェック
    if row["expires_at"] <= datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S"):
        delete_session(conn, token)
        return None
    return {"id": row["id"], "name": row["name"],
            "display_name": row["display_name"], "coins": 1000}

def delete_session(conn, token: str) -> None:
    if not token:
        return
    conn.execute("DELETE FROM sessions WHERE token = ?", (token,))

print("✅ session 操作関数 4 つ ready")

Spiral 3 — フロントが Token を保管 + Authorization ヘッダで送る

フロント (web/app.js) はすでに Token を扱える状態に書かれています。 具体的には:

  • レスポンスに token が含まれていれば localStorage に保存
  • 以後のリクエストで Authorization: Bearer <token> ヘッダを自動付与
  • ログアウトで Token を消去

つまりサーバ側を直したらフロントは何もしなくていい。 試してみましょう:

🧪 動作確認
  1. フロントで「ログアウト」 → Token 消去
  2. alice / secret123 でログイン → 200、 デバッグコンソールにレスポンスの token フィールドが見える
  3. 同じセッションで何かリクエストを投げる (例: 「最新化」 ボタンで Box 取得)
  4. デバッグコンソール → リクエストヘッダに Authorization: Bearer ABC... が付いている

%%sql SELECT * FROM sessions; を Colab で打つと、 発行されたトークンと有効期限の行が見えます。 ログインするたびに 1 行増える。

Spiral 4 — /api/me と /api/logout をセッション対応に

最後の仕上げ。 ハードコードだった 2 つを本物に。

📒 セル 6-F — /api/me と /api/logout 
@route("GET", "/api/me")
def me(h):
    # Authorization: Bearer <token> ヘッダを取り出す
    auth_header = h.headers.get("Authorization", "")
    if not auth_header.lower().startswith("bearer "):
        raise unauthorized()
    token = auth_header.split(" ", 1)[1].strip()

    with get_conn() as conn:
        user = lookup_session(conn, token)
    if user is None:
        raise unauthorized()
    h._json(200, {"user": user})


@route("POST", "/api/logout")
def logout(h):
    auth_header = h.headers.get("Authorization", "")
    token = ""
    if auth_header.lower().startswith("bearer "):
        token = auth_header.split(" ", 1)[1].strip()
    with get_conn() as conn:
        delete_session(conn, token)
    h._json(200, {"ok": True})

print("✅ /api/me と /api/logout がセッション対応に")

🧪 動作確認 — ここがクライマックス

  1. フロントで「ログアウト」 → 登録/ログイン画面に戻る
  2. alice / secret123 でログイン → ガチャ画面 (= 当たり前)
  3. ブラウザのページを丸ごとリロード (F5)
  4. フロントが localStorage から token を取り出して GET /api/me を投げる
  5. サーバが「あなたは alice」 と判定して 200 を返す
  6. ガチャ画面のままになる (= 「リロードしてもログイン状態が残った」)

本物のセッション管理が成立しました。 サーバを再起動しても、 ブラウザを再起動しても、 Token を消さない限りアクセス可能。

もう一度「ログアウト」 を押すと:

  1. サーバが sessions から行を DELETE
  2. フロントが localStorage から token を消去
  3. 登録画面に戻る
  4. 同じ Token を手で復活させても、 サーバは「そんな token は知らない」 で 401 を返す (= サーバ側で確実に無効化された)

require_user ヘルパで定型句を縮める

認証必須エンドポイントが Ch.7 / Ch.8 で増えるので、 共通処理を 1 関数にまとめておきます。

📒 セル 6-G — require_user (= Ch.7 以降で活躍) 
def require_user(h, conn):
    """認証必須エンドポイントの先頭で呼ぶ。 token が無効なら 401。"""
    auth_header = h.headers.get("Authorization", "")
    if not auth_header.lower().startswith("bearer "):
        raise unauthorized()
    token = auth_header.split(" ", 1)[1].strip()
    user = lookup_session(conn, token)
    if user is None:
        raise unauthorized()
    return user

# /api/me を簡略化
@route("GET", "/api/me")
def me(h):
    with get_conn() as conn:
        user = require_user(h, conn)
    h._json(200, {"user": user})

print("✅ require_user ready")

これで Ch.7 の /api/gacha/pull、 Ch.8 の /api/box が user = require_user(h, conn) 1 行で済みます。

本章のまとめ

  • パスワードはハッシュ化して保存。 ソルトと反復回数でレインボーテーブル/総当たりを難しくする
  • パスワードの照合は hmac.compare_digest でタイミング攻撃に対抗
  • HTTP はステートレス → 「あなたは alice」 を覚えるには毎回トークンを送る必要がある
  • Cookie ではなく Bearer Token 方式を採用 (Colab + クロスオリジン環境で扱いやすい)
  • sessions テーブルにトークンを保存、 期限切れは自動削除、 ログアウトで明示削除
  • require_user ヘルパで、 認証必須エンドポイントの定型句を 1 行に
📝 本番で気をつけたいこと
  • HTTPS 必須 (Bearer Token がネットワーク上で平文で流れるため)
  • 定期的に DELETE FROM sessions WHERE expires_at < ... で古い行を掃除
  • パスワードは pbkdf2 でも実用十分だが、 Argon2 / bcrypt の方がより推奨
  • 同一ユーザーの複数端末ログインを許すか、 制限するかの設計判断
