第 7 章 — ユーザー管理を導入

Ch.5/6 でガチャと Box が動きました。 でもこの状態だと:

  • 誰がアクセスしても全員「guest」
  • 友達と同じ画面を開くと、 自分のドラゴンが友達にも見えてしまう
  • 友達がガチャを引くと自分のコインも一緒に減る

これは「自分のドラゴン」 「私のスライム」 が成立しないので、 ゲームとして致命的。 この章でユーザー登録 / ログイン / 個別 Box を実現します。

5 ステップで:

  1. POST /api/register をハードコードから実 INSERT に
  2. パスワードをハッシュ化して保存 (= DB が漏れても元のパスがバレない)
  3. sessions テーブル + Bearer Token でログイン状態を持つ
  4. 「リクエストの送り主を特定」 する require_user ヘルパ
  5. 既存の pull / box / me を「ログイン中ユーザーの操作」 に書き換え

7.2 パスワードをハッシュ化

DB に平文でパスワードを保存するのは大事故の温床。 「DB 漏洩 → 即全員のパスバレ」 となる。 ハッシュ化すると、 漏れても元のパスは復元できなくなる。

📚 コラム: ハッシュ vs 暗号

初心者が混同しがちなので違いをハッキリ:

ハッシュ関数(共通鍵) 暗号
方向一方向 (戻せない)双方向 (鍵があれば戻せる)
例SHA-256, MD5, bcrypt, pbkdf2AES, ChaCha20
用途パスワード保管、 改ざん検知通信秘密保持、 ファイル暗号化
同じ入力 → 出力常に同じ (= 決定的)初期値で変えるのが普通

パスワード保管に必要なのは「漏洩しても元を復元できない」 性質。 だから暗号 (戻せる) ではなく ハッシュ (戻せない) を使う。 ログイン時は「入力されたパスを同じ関数に通して、 保存値と比較」 で照合。

SHA-256 を 1 回かけるだけでは弱い

ハッシュ関数は同じ入力に同じ出力を返すので、 事前計算した変換表 (レインボーテーブル) が攻撃に使えます。 対策が 2 つ:

  • ソルト (salt): ユーザーごとにランダムな byte 列を作って計算に混ぜる → 同じパスでもユーザーごとに違うハッシュ → 事前計算表が使えない
  • 反復回数: 同じハッシュを何万回も繰り返す → 1 回の計算が遅くなる → 総当たり攻撃の手間が桁違いに増える

これを束ねたのが pbkdf2。 Python 標準 hashlib に最初から入っています。

📒 セル 7-B — hash_password / verify_password 
import base64, hashlib, hmac, os

_ALGO = "sha256"
_ITER = 200_000        # 200,000 回繰り返す
_SALT_BYTES = 16
_DK_BYTES = 32

def hash_password(password):
    """パスワードをハッシュ化 → 保存用文字列を返す。
       形式: pbkdf2_sha256$200000$$"""
    salt = os.urandom(_SALT_BYTES)
    dk = hashlib.pbkdf2_hmac(_ALGO, password.encode("utf-8"),
                             salt, _ITER, dklen=_DK_BYTES)
    return "$".join([
        f"pbkdf2_{_ALGO}", str(_ITER),
        base64.b64encode(salt).decode(),
        base64.b64encode(dk).decode(),
    ])

def verify_password(password, stored):
    """入力パス + 保存ハッシュ で照合 (タイミング攻撃対策込み)。"""
    try:
        algo, iter_s, salt_b64, hash_b64 = stored.split("$")
    except ValueError:
        return False
    if not algo.startswith("pbkdf2_"):
        return False
    digest_name = algo.split("_", 1)[1]
    iters = int(iter_s)
    salt = base64.b64decode(salt_b64)
    expected = base64.b64decode(hash_b64)
    actual = hashlib.pbkdf2_hmac(digest_name, password.encode("utf-8"),
                                 salt, iters, dklen=len(expected))
    return hmac.compare_digest(actual, expected)

# 動作確認
h1 = hash_password("hunter2")
h2 = hash_password("hunter2")
print("h1:", h1[:60], "...")
print("h2:", h2[:60], "...")
print("h1 == h2 ?  ", h1 == h2)                          # ソルトで毎回違う
print("verify 正解:", verify_password("hunter2", h1))    # True
print("verify 不正:", verify_password("HUNTER2", h1))    # False
📚 コラム: hmac.compare_digest って何が違う?

普通の == 比較は、 文字列を頭から見比べて違いが出た瞬間に return する。 だから「最初の 1 byte が合っているか」 と「最後まで全て合っているか」 で応答時間に差が出る。 攻撃者が応答時間を測れば、 「正解に近い byte」 を当てていける (タイミング攻撃)。

hmac.compare_digest は文字列の長さを揃えて常に同じ時間で比較する。 パスワード照合や HMAC のシグネチャ検証には必ずこれを使う、 が業界の常識。

7.3 sessions テーブル + Bearer Token

📚 コラム: HTTP はステートレス

HTTP の重要な性質: 1 つの往復ごとに完結していて、 サーバはリクエスト間の関係を覚えない。 ステートレス (= 状態を持たない)。

だから「あなたは alice さん」 という情報は、 毎回のリクエストに何かを添えて送る必要があります。 この「何か」 = セッショントークン。

添える方法は主に 2 通り:

  1. Cookie: ブラウザが自動で添えてくれる
  2. Authorization ヘッダ (Bearer Token): クライアント側で保管して、 毎回明示的に付ける

本教材は file:// フロントや別ポート配信などのクロスオリジン環境を扱うので、 Cookie 設定の落とし穴を避けつつ、 業界でも広く使われる Bearer Token 方式を採用します。 SPA や REST API、 モバイルアプリの定番。

sessions テーブル

📒 SQL 7-D — sessions テーブル (psql で実行) 
CREATE TABLE IF NOT EXISTS sessions (
    token      TEXT        PRIMARY KEY,
    user_id    BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON sessions(user_id);

セッション操作の関数

📒 セル 7-E — セッション操作 
import secrets
from datetime import datetime, timedelta, timezone

SESSION_TTL = timedelta(days=7)

def new_session_token():
    """十分に長いランダムトークン (256bit, URL-safe)。"""
    return secrets.token_urlsafe(32)

def create_session(conn, user_id):
    token = new_session_token()
    expires = (datetime.now(timezone.utc) + SESSION_TTL).strftime("%Y-%m-%d %H:%M:%S")
    conn.execute("INSERT INTO sessions (token, user_id, expires_at) VALUES (%s, %s, %s)",
                 (token, user_id, expires))
    return token, expires

def lookup_session(conn, token):
    """token から user 情報を引く。 期限切れ / 不在は None。"""
    if not token: return None
    cur = conn.execute(
        """
        SELECT u.id, u.name, u.display_name, u.coins, s.expires_at
          FROM sessions s
          JOIN users    u ON u.id = s.user_id
         WHERE s.token = ?
        """, (token,))
    row = cur.fetchone()
    if row is None: return None
    if row["expires_at"] <= datetime.now(timezone.utc).strftime("%Y-%m-%d %H:%M:%S"):
        delete_session(conn, token)
        return None
    return {"id": row["id"], "name": row["name"],
            "display_name": row["display_name"], "coins": row["coins"]}

def delete_session(conn, token):
    if not token: return
    conn.execute("DELETE FROM sessions WHERE token = %s", (token,))

print("✅ session 操作関数 ready")

7.4 require_user ヘルパ + /api/me /logout を本物に

認証必須エンドポイントの先頭で呼ぶヘルパ関数を作ります。 Authorization ヘッダから token を取り出し、 sessions に問い合わせて user を返す。

📒 セル 7-G — require_user + /api/me + /api/logout 
def require_user(h, conn):
    """認証必須ハンドラの先頭で呼ぶ。 トークン無効なら 401。"""
    auth_header = h.headers.get("Authorization", "")
    if not auth_header.lower().startswith("bearer "):
        raise unauthorized()
    token = auth_header.split(" ", 1)[1].strip()
    user = lookup_session(conn, token)
    if user is None:
        raise unauthorized()
    return user

@route("GET", "/api/me")
def me(h):
    with get_conn() as conn:
        user = require_user(h, conn)
    h._json(200, {"user": user})

@route("POST", "/api/logout")
def logout(h):
    auth_header = h.headers.get("Authorization", "")
    token = ""
    if auth_header.lower().startswith("bearer "):
        token = auth_header.split(" ", 1)[1].strip()
    with get_conn() as conn:
        delete_session(conn, token)
    h._json(200, {"ok": True})

print("✅ /api/me と /api/logout がセッション対応に")

重要: /api/me は今や「ログイン中なら user、 そうでなければ 401」 を返します。 Ch.5 で「常に guest を返す」 にしていたのから変わりました。 これでフロントは:

  1. 起動時に /api/me 投げる → 401 (まだトークン無し)
  2. 登録/ログインフォームを出す
  3. ユーザーが登録 → token を localStorage に保存 → ガチャ画面
  4. リロードしても、 トークンが localStorage にあるので /api/me 200 で復帰

@route("POST", "/api/gacha/pull")
def gacha_pull(h):
    body = h._read_json()
    gacha_id = body.get("gacha_id")
    if not isinstance(gacha_id, int):
        raise bad_request("gacha_id は整数で")

    with get_conn() as conn:
        user = require_user(h, conn)                  # ← ここが変わった

        g = conn.execute("SELECT id, name, price FROM gachas WHERE id = %s",
                         (gacha_id,)).fetchone()
        if g is None:
            raise not_found("そのガチャは存在しません")

        coins_now = conn.execute(
            "SELECT coins FROM users WHERE id = %s", (user["id"],)
        ).fetchone()["coins"]
        if coins_now < g["price"]:
            raise bad_request(f"コインが足りません (必要 {g['price']} / 所持 {coins_now})")

        pool = fetch_pool(conn, gacha_id)
        if not pool:
            raise bad_request("そのガチャに排出設定がありません")
        won = draw(pool)

        new_coins = conn.execute(
            "UPDATE users SET coins = coins - ? WHERE id = %s RETURNING coins",
            (g["price"], user["id"]),                # ← user_id をログイン中の人に
        ).fetchone()["coins"]

        obtained_at = conn.execute(
            "INSERT INTO user_characters (user_id, character_id) VALUES (%s, %s) "
            "RETURNING obtained_at",
            (user["id"], won.character_id),         # ← ここも
        ).fetchone()["obtained_at"]

    h._json(200, {
        "gacha":     {"id": g["id"], "name": g["name"], "price": g["price"]},
        "character": {"id": won.character_id, "name": won.name,
                      "rarity": won.rarity, "emoji": won.emoji},
        "obtained_at": obtained_at,
        "coins": new_coins,
    })


@route("GET", "/api/box")
def box(h):
    with get_conn() as conn:
        user = require_user(h, conn)                 # ← ここも

        rows = conn.execute("""
            SELECT c.id, c.name, c.rarity, c.emoji,
                   COUNT(*)            AS count,
                   MIN(uc.obtained_at) AS first_obtained_at,
                   MAX(uc.obtained_at) AS last_obtained_at
              FROM user_characters uc
              JOIN characters       c ON c.id = uc.character_id
             WHERE uc.user_id = ?
             GROUP BY c.id
             ORDER BY c.rarity DESC, c.id
        """, (user["id"],)).fetchall()

        total_pulls = conn.execute(
            "SELECT COUNT(*) AS n FROM user_characters WHERE user_id = %s",
            (user["id"],),
        ).fetchone()["n"]

    h._json(200, {
        "user":        user,
        "total_pulls": total_pulls,
        "items":       [dict(r) for r in rows],
    })

print("✅ pull / box が「ログイン中ユーザーの操作」 に")

本章のまとめ

  • register / login を本実装。 パスワードは pbkdf2 でハッシュ化して保存
  • HTTP はステートレス → 「あなたは alice さん」 を覚えさせるには毎回 token を送る必要がある
  • Bearer Token 方式 = Authorization ヘッダで送る、 SPA / REST API の定番
  • require_user ヘルパで認証必須エンドポイントの定型句を 1 行に
  • 既存の pull / box を user-aware に直すことで、 「ユーザーごとの Box」 が成立した
📝 本番で気をつけたいこと
  • HTTPS 必須 (Bearer Token がネットワーク上で平文で流れるため)
  • 定期的に DELETE FROM sessions WHERE expires_at < ... で古い行を掃除
  • パスワードは pbkdf2 でも十分だが、 Argon2 / bcrypt の方がより推奨
  • 同一ユーザーの複数端末ログインを許すか、 制限するかの設計判断
