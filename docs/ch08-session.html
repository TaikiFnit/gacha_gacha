第 8 章 — 仕上げ: ファイル分割と smoke テスト

ここまでの 7 章でガチャシステムは 本当に動くもの になりました。 最後の仕上げとして、 肥大化した my_server.py をきちんと分け、 機械的に動作確認できるテスト を入れて、 明日の自分や仲間が触っても安心な状態にします。

3 つのトピック:

  1. my_server.py を 4 ファイルに分割
  2. smoke テスト (curl ベースの E2E) を書く
  3. (任意) ユニットテスト を 1 つ書く例

8.1 なぜ分割するのか

ここまで my_server.py は 1 ファイル 200〜300 行になっていると思います。 まだ読めるサイズですが、 これがチームで複数人が触るとなると:

  • 「ガチャ抽選を変えたい」 だけの人が、 関係ない認証コードまで読む羽目に
  • git の diff が膨らみ、 コードレビューが大変
  • 「authモジュールだけテストしたい」 が出来ない

役割で分けると、 これらが解消します。 既に server/db.py, server/auth.py, server/gacha.py は分けてあるので、 残りは my_server.py を server/app.py として整理し、 ルートとサーバ起動のみにする話です。

8.2 4 ファイル構成への移行

ファイル役割主な中身
server/db.pyDB 接続get_conn / healthcheck
server/auth.py認証hash_password / verify_password / create_session / lookup_session / delete_session
server/gacha.py抽選fetch_pool / draw / GachaItem

移行手順: my_server.py の中身を server/app.py にコピーして、 imports を server. 経由に書き直し、 起動コマンドを変えるだけ。

server/app.py の __main__ ブロックは リポジトリ完成版 と同じく: 

def main() -> int:
    if not healthcheck():
        print("PostgreSQL に接続できません。 docker compose up -d を先に")
        return 1
    addr = ("0.0.0.0", 8000)
    server = ThreadingHTTPServer(addr, App)
    print(f"listening on http://localhost:{addr[1]}")
    print("ルート一覧:")
    for (m, p) in sorted(ROUTES):
        print(f"  {m:5s} {p}")
    try:
        server.serve_forever()
    except KeyboardInterrupt:
        print("\nbye")
    finally:
        server.server_close()
    return 0


if __name__ == "__main__":
    raise SystemExit(main())

HTTPServer ではなく ThreadingHTTPServer を使うと、 複数のリクエストを同時に処理できます (1 リクエストが遅くても他がブロックされない)。

8.3 smoke テスト — curl で全エンドポイントを叩く

動くと信じる、 ではなく機械が確かめてくれる 状態を作ります。 最も軽量なやり方は curl + シェルスクリプト。 サーバが起動していれば 何度でも実行できる、 後の章 (拡張) を書くときの安全網になります。

📄 tests/smoke_curl.sh (新規) 
#!/usr/bin/env bash
# 本物の gacha_gacha API に対する smoke テスト。
#
# 必要なもの:
#   - docker compose up -d   (Postgres 起動)
#   - python -m server.app   (API サーバ起動)
#   - jq (任意 / きれいに表示用)
#
# 使い方:
#   bash tests/smoke_curl.sh
set -euo pipefail

BASE_URL=${BASE_URL:-http://localhost:8000}
USER_NAME=${USER:-smoke_user_$$}      # 毎回ユニーク
PASSWORD=${PASSWORD:-smokepass123}
COOKIES=$(mktemp); trap 'rm -f "$COOKIES"' EXIT

JQ=$(command -v jq || true)
fmt() { if [ -n "$JQ" ]; then $JQ; else cat; fi; }

call() {
  local method=$1 path=$2 body=${3:-}
  local args=( -sS -X "$method" -b "$COOKIES" -c "$COOKIES"
               -H "Content-Type: application/json"
               -w '\nHTTP_STATUS:%{http_code}\n'
               "$BASE_URL$path" )
  [ -n "$body" ] && args+=( -d "$body" )
  curl "${args[@]}"
}

echo "== 1. register =="
call POST /api/register \
  "{\"name\":\"$USER_NAME\",\"password\":\"$PASSWORD\",\"display_name\":\"Smoker\"}" | fmt

echo; echo "== 2. me =="
call GET /api/me | fmt

echo; echo "== 3. gacha list =="
call GET /api/gacha/list | fmt

echo; echo "== 4. pull x 3 =="
for i in 1 2 3; do
  echo "-- pull $i --"
  call POST /api/gacha/pull '{"gacha_id":1}' | fmt
done

echo; echo "== 5. box =="
call GET /api/box | fmt

echo; echo "== 6. logout =="
call POST /api/logout | fmt

echo; echo "== 7. me after logout (expect 401) =="
call GET /api/me | fmt

echo; echo "smoke test finished. user=$USER_NAME"

💡 解説

  • -c $COOKIES でクッキージャーに保存、 -b $COOKIES で次のリクエストに付ける = ブラウザの動きを再現
  • 毎回ユニークな name ($$ = PID 埋め込み) で UNIQUE 制約と衝突しないように
  • set -euo pipefail で、 1 ステップでも失敗したら即終了
  • jq が無くても動くようフォールバック

8.4 (任意) ユニットテスト — DB 抜きで純粋関数だけ

smoke テストは API 全体の通しを確認します。 一方 auth.hash_password や gacha.draw のように 純粋関数 は、 DB を立てずに もっと素早く検証できます。

📄 tests/test_unit.py (新規) 
"""DB 抜きユニットテスト。

実行:
    python tests/test_unit.py
"""
import pathlib, sys, random
sys.path.insert(0, str(pathlib.Path(__file__).resolve().parent.parent))
from server import auth, gacha

_failed = False
def expect(label, cond, detail=""):
    global _failed
    print(f"  {'PASS' if cond else 'FAIL'}  {label}  {'' if cond else detail}")
    if not cond: _failed = True

def test_password():
    print("\n[auth]")
    h = auth.hash_password("hunter2")
    expect("正しいパスでverify",   auth.verify_password("hunter2", h))
    expect("間違ったパスでreject", not auth.verify_password("HUNTER2", h))
    expect("同じパスでも違うhash", auth.hash_password("a") != auth.hash_password("a"))

def test_gacha():
    print("\n[gacha]")
    pool = [
        gacha.GachaItem(1, "A", 1, "🟢", 75),
        gacha.GachaItem(2, "B", 5, "🐉", 25),
    ]
    rng = random.Random(0)
    counts = {1: 0, 2: 0}
    for _ in range(10_000):
        counts[gacha.draw(pool, rng=rng).character_id] += 1
    expect(f"分布近似 (A: {counts[1]/100:.1f}% ≈ 75%)", abs(counts[1]/10_000 - 0.75) < 0.02)

if __name__ == "__main__":
    test_password()
    test_gacha()
    print("\n", "FAILED" if _failed else "PASSED ✓")
    raise SystemExit(1 if _failed else 0)

8.5 リポジトリ完成版との比較

ここまでで君の ~/gacha_gacha/ は、 リポジトリ直下のものと 機能としてほぼ同じになっているはずです。 細かな差分:

  • リポジトリ版には CORS ALLOWED_ORIGINS が定数化、 環境変数で port を受け取る等の小工夫が入っている
  • tests/test_e2e_sqlite.py という SQLite 互換アダプタ経由の E2E テストもある (= Docker 不要で 27 ケース通る)
  • このテストハーネスは「server.db.get_conn をモンキーパッチして SQLite に喋らせる」 という小芸でできている

興味があれば tests/test_e2e_sqlite.py と tests/sqlite_adapter.py を読んでみてください。 「PG と SQLite で SQL 方言の差を吸収するアダプタ」 を 100 行ぐらいで書いていて、 Postgres を立てなくてもユニットテスト感覚で API 全体を回せます。

本章のまとめ

  • 1 ファイル肥大化 → 役割で分割。 4 つのモジュールにすると見通しが一気によくなる
  • smoke テストは「動く」 を機械化するための最小コスト な保険
  • ユニットテストは「DB 不要で速い」。 純粋関数を分離しておくと書きやすい
  • テストがあると拡張に進める = Ch.9 へ
