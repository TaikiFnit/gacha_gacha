Chapter 7 所要時間: 90〜120 分 形式: 5 スパイラルで gacha 抽選を完成

第 7 章 — ガチャ抽選を本実装する

ここまでハードコードでドラゴンしか出ない状態でした。 この章でようやく このシステムの本丸 — 重み付き乱択 + コイン消費 + DB に履歴を残す — を本実装します。 さらに 「コインだけ減ってキャラもらえないバグ」 を意図的に発生させてから トランザクションで救う、 というストーリー仕立て。

5 スパイラルで:

  1. 必要なテーブルを準備 (users.coins / characters / gachas / gacha_items / user_characters)
  2. GET /api/gacha/list をハードコード → 実 DB SELECT に
  3. 重み付き乱択 (draw 関数) を書いて、 シミュレーションで確かめる
  4. POST /api/gacha/pull を書く — トランザクション無し版でわざとバグを発生
  5. 同じ pull にトランザクションを入れて、 DB が壊れない形に直す

Spiral 1 — /api/gacha/list を実 DB から

Ch.4 / Ch.5 でハードコードしていたガチャ筐体一覧を、 実 DB から取ってくるように。 ガチャごとの 排出キャラ数と weight 合計 も JOIN+COUNT+SUM で。

📒 セル 7-D — gacha_list を本物に 
@route("GET", "/api/gacha/list")
def gacha_list(h):
    with get_conn() as conn:
        rows = conn.execute("""
            SELECT g.id, g.name, g.price,
                   COUNT(gi.id)               AS pool_size,
                   COALESCE(SUM(gi.weight), 0) AS total_weight
              FROM gachas g
              LEFT JOIN gacha_items gi ON gi.gacha_id = g.id
             GROUP BY g.id
             ORDER BY g.id
        """).fetchall()
    h._json(200, {"gachas": [dict(r) for r in rows]})

print("✅ /api/gacha/list が実 DB から返すように")

🧪 動作確認

  • フロントをリロード or 「最新化」 → ガチャ一覧が seed 通り (通常ガチャ 12 種、 プレミアム 7 種)
  • LEFT JOIN = 「排出設定が無いガチャがあっても 0 件で出てくる」 ようにする保険

Spiral 2 — 重み付き乱択 (draw 関数)

ガチャの肝は「キャラごとに違う出やすさ」。 これを「乱数 + weight」 で実装します。 アルゴリズムは古典的:

  1. weight の合計を分母にして、 0〜合計 の一様乱数 r を 1 つ引く
  2. 各キャラの weight を順に足していき、 累積が r を超えた時点のキャラが当選
📚 コラム: 「一様乱数」 と random.choices

一様乱数 = 与えた範囲の中のどの値も等しい確率で選ばれる乱数。 Python の random.uniform(0, 1) や random.random() がこれ。

Python 標準の random.choices(items, weights=[...], k=1) は、 上の累積和+一様乱数の アルゴリズムをそのまま実装してくれます。 自分で書く必要はないが、 仕組みは理解しておくと便利。

本物のセキュリティ用途 (パスワード生成、 セッショントークンなど) には secrets.token_urlsafe() や random.SystemRandom() という 暗号学的乱数を使います。 ガチャの抽選にも使う方が望ましい (= プレイヤーが「次に出るキャラを予測」 できないように)。

📒 セル 7-E — draw 関数 + シミュレーション 
import random
from dataclasses import dataclass

@dataclass
class GachaItem:
    character_id: int
    name: str
    rarity: int
    emoji: str
    weight: int

def fetch_pool(conn, gacha_id):
    """指定ガチャの排出プールを取ってくる。"""
    rows = conn.execute("""
        SELECT c.id AS character_id, c.name, c.rarity, c.emoji, gi.weight
          FROM gacha_items gi
          JOIN characters c ON c.id = gi.character_id
         WHERE gi.gacha_id = ?
         ORDER BY c.rarity, c.id
    """, (gacha_id,)).fetchall()
    return [GachaItem(**dict(r)) for r in rows]

def draw(pool, rng=None):
    """重み付き乱択を 1 回行う。"""
    if not pool:
        raise ValueError("空のプール")
    rng = rng or random.SystemRandom()
    weights = [item.weight for item in pool]
    return rng.choices(pool, weights=weights, k=1)[0]


# シミュレーションで分布を確かめる (10万回引いて weight 比に近づくか)
from collections import Counter
with get_conn() as conn:
    pool = fetch_pool(conn, 1)
total_w = sum(p.weight for p in pool)
counts = Counter()
N = 100_000
rng = random.Random(42)         # 再現可能性のため固定 seed
for _ in range(N):
    counts[draw(pool, rng=rng).name] += 1

print("通常ガチャ 10万回シミュレーション:")
for p in sorted(pool, key=lambda x: -x.weight):
    expected = p.weight / total_w * 100
    actual   = counts[p.name] / N * 100
    print(f"  {p.name:14s} 期待 {expected:5.2f}%  実測 {actual:5.2f}%")

Spiral 3 — pull を書く ⚠️ トランザクション無し版

ガチャを引く処理に必要なのは:

  1. ユーザーのコイン残高を確認
  2. 抽選
  3. コインを減らす (UPDATE)
  4. 履歴に追加 (INSERT)

自然に書くとこうなる:

⚠️ セル 7-F — トランザクション無しの危ない pull 
import sqlite3, random as _r

@route("POST", "/api/gacha/pull")
def gacha_pull_buggy(h):
    body = h._read_json()
    gacha_id = body.get("gacha_id")
    if not isinstance(gacha_id, int):
        raise bad_request("gacha_id は整数で")

    # ⚠️ get_conn (= 自動トランザクション付き) ではなく、 isolation_level=None で
    # 1 文ずつ自動コミットする「危ない」 接続を意図的に使う。
    conn = sqlite3.connect("gacha.db", isolation_level=None)
    conn.row_factory = sqlite3.Row
    try:
        # 認証
        auth_h = h.headers.get("Authorization", "")
        token = auth_h.split(" ", 1)[1].strip() if auth_h.lower().startswith("bearer ") else ""
        cur = conn.execute(
            "SELECT u.id, u.coins FROM sessions s JOIN users u ON u.id=s.user_id WHERE s.token=?",
            (token,),
        )
        user = cur.fetchone()
        if user is None: raise unauthorized()

        # ガチャ情報
        cur = conn.execute("SELECT id, name, price FROM gachas WHERE id = ?", (gacha_id,))
        g = cur.fetchone()
        if g is None: raise not_found("ガチャ無し")

        if user["coins"] < g["price"]:
            raise bad_request(f"コインが足りません ({user['coins']} < {g['price']})")

        # プール取得 + 抽選
        rows = conn.execute("""
            SELECT c.id AS character_id, c.name, c.rarity, c.emoji, gi.weight
              FROM gacha_items gi JOIN characters c ON c.id=gi.character_id
             WHERE gi.gacha_id = ? ORDER BY c.rarity, c.id
        """, (gacha_id,)).fetchall()
        pool = [GachaItem(**dict(r)) for r in rows]
        won = draw(pool)

        # ⚠️ 1: コインを減らす (即コミットされる)
        conn.execute("UPDATE users SET coins = coins - ? WHERE id = ?", (g["price"], user["id"]))

        # ⚠️ 2: ここで何かが落ちる可能性がある (= ネットワーク瞬断、 サーバ再起動、 例外)
        #     50% の確率でクラッシュをシミュレートする
        if _r.random() < 0.5:
            raise Exception("シミュレート: 履歴 INSERT 直前で何かが落ちた")

        # ⚠️ 3: 履歴 INSERT
        conn.execute("INSERT INTO user_characters (user_id, character_id) VALUES (?, ?)",
                     (user["id"], won.character_id))

        # 結果
        new_coins_row = conn.execute("SELECT coins FROM users WHERE id=?", (user["id"],)).fetchone()
        h._json(200, {
            "gacha":     {"id": g["id"], "name": g["name"], "price": g["price"]},
            "character": {"id": won.character_id, "name": won.name,
                          "rarity": won.rarity, "emoji": won.emoji},
            "obtained_at": "now",
            "coins": new_coins_row["coins"],
        })
    finally:
        conn.close()

print("⚠️ pull の危ない版を仕掛けた (50% でクラッシュする)")

🧪 バグを実際に体験する

フロントで何度かガチャを引いてみてください。 半分くらい「⚠️ サーバから返ってきませんでした」 (500 エラー) になります。 そのあと Colab で確認:

📒 セル 7-G — DB の整合性をチェック 
%%sql
SELECT u.id, u.name, u.coins,
       (SELECT COUNT(*) FROM user_characters uc WHERE uc.user_id = u.id) AS owned
  FROM users u;

たぶん次のような結果が見えるはず:

⚠️ 期待される (= バグった) 結果 
id  name   coins  owned
--  -----  -----  -----
1   alice    600      4   ← 「コインを 4 回引いたぶん減ってるのに、 owned は 4 (= 5 回中 4 回成功)」
                          ← 1 回ぶん「コインだけ消えた」

これがバグ。 コインは減っているのに、 履歴には追加されていない。 ユーザーから見れば 「コイン取られたのにキャラもらえてない」 = 大クレーム案件。

原因は明らか: ステップ 1 (UPDATE) は即コミットされている (= 確定済み)。 ステップ 3 (INSERT) は 実行前に例外で死んだ。 結果として 1 だけが残った。

Spiral 4 — トランザクションで救う

📚 コラム: トランザクションって?

トランザクション: 複数の DB 操作を「まとめて 1 セット」 として扱う仕組み。 セットの中身は全成功 or 全失敗 しかない。 これを 原子性 (Atomicity) と呼ぶ。

SQL での書き方: 

BEGIN;
   UPDATE users SET coins = coins - 100 WHERE id = 1;
   INSERT INTO user_characters (user_id, character_id) VALUES (1, 5);
COMMIT;

BEGIN から COMMIT までが 1 つのトランザクション。 途中で何か失敗したら ROLLBACK で全てを「無かったこと」 にできる。

Python 側でも、 with get_conn() as conn: ブロックを使えば正常終了で COMMIT、 例外で ROLLBACK が自動で起こります。 これが本教材の get_conn() ヘルパが やっていること。 自分で書く場合は conn.execute("BEGIN") / "COMMIT" / "ROLLBACK" を直接呼ぶ。

DB の世界では ACID という用語があり、 トランザクションが提供する 4 性質の頭文字:

  • Atomicity (原子性) — 全成功か全失敗
  • Consistency (整合性) — 制約は常に守られる
  • Isolation (独立性) — 同時実行しても他のトランザクションに干渉しない
  • Durability (永続性) — COMMIT したら停電しても消えない

Ch.7 で必要なのは主に A (原子性)。 残り 3 つは別の場面 (並行アクセス、 障害耐性) で効いてくる。

📒 セル 7-H — pull の最終形 (トランザクション付き) 
@route("POST", "/api/gacha/pull")
def gacha_pull(h):
    body = h._read_json()
    gacha_id = body.get("gacha_id")
    if not isinstance(gacha_id, int):
        raise bad_request("gacha_id は整数で")

    # get_conn() は with ブロックを抜けるときに自動コミット、 例外で自動ロールバック。
    # = ブロック全体が 1 つのトランザクション。
    with get_conn() as conn:
        user = require_user(h, conn)

        # ガチャ情報
        cur = conn.execute("SELECT id, name, price FROM gachas WHERE id = ?", (gacha_id,))
        g = cur.fetchone()
        if g is None:
            raise not_found("そのガチャは存在しません")

        # コイン残高チェック
        cur = conn.execute("SELECT coins FROM users WHERE id = ?", (user["id"],))
        coins_now = cur.fetchone()["coins"]
        if coins_now < g["price"]:
            raise bad_request(f"コインが足りません (必要 {g['price']} / 所持 {coins_now})")

        # プール取得 + 抽選
        pool = fetch_pool(conn, gacha_id)
        if not pool:
            raise bad_request("そのガチャに排出設定がありません")
        won = draw(pool)

        # 同じ「シミュレート障害」 を入れて、 トランザクションで救われることを確かめる
        # (試したら本番では消す)
        # if _r.random() < 0.5:
        #     raise Exception("シミュレート障害")

        # 2 つの操作を 1 つのトランザクションに束ねる
        cur = conn.execute(
            "UPDATE users SET coins = coins - ? WHERE id = ? RETURNING coins",
            (g["price"], user["id"]),
        )
        new_coins = cur.fetchone()["coins"]

        cur = conn.execute(
            "INSERT INTO user_characters (user_id, character_id) VALUES (?, ?) "
            "RETURNING obtained_at",
            (user["id"], won.character_id),
        )
        obtained_at = cur.fetchone()["obtained_at"]

    h._json(200, {
        "gacha":     {"id": g["id"], "name": g["name"], "price": g["price"]},
        "character": {"id": won.character_id, "name": won.name,
                      "rarity": won.rarity, "emoji": won.emoji},
        "obtained_at": obtained_at,
        "coins": new_coins,
    })

print("✅ pull が transaction-safe に")

本章のまとめ

  • ALTER TABLE で既存テーブルに列を追加できる
  • 重み付き乱択 = 累積和 + 一様乱数。 random.choices(weights=...) がそれ
  • 大数の法則を使って実装の正しさをシミュレーションで検証するのが定番
  • 2 つ以上の DB 操作が 1 セットなら必ずトランザクションで束ねる。 途中で何が起きても DB は無傷
  • with get_conn() as conn: パターンが「成功で COMMIT、 例外で ROLLBACK」 を自動でやってくれる
