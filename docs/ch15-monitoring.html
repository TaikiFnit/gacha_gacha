Chapter 15 所要時間: 90〜120 分 形式: 構造化ログ + メトリクス + readiness probe

第 15 章 — 監視・ログ・運用

ガチャシステムが動き始めたら、 次に必要なのは「動いている事実を観測できる」仕組みです。 ログ、 メトリクス、 ヘルスチェックの 3 種を入れて、 サーバが壊れる前 / 壊れた瞬間に 気付ける状態を作ります。

🎯 この章のゴール
  1. logging モジュールで JSON 構造化ログを stdout に出す
  2. アクセスログをミドルウェア的に全 API へ自動付与
  3. 遅いクエリを Postgres 側 (auto_explain) で検出
  4. GET /api/metrics で Prometheus 互換のテキストを返す
  5. GET /api/ready で DB 接続まで含めた readiness を返す

15.1 print から logging へ

これまで print() で済ませていたデバッグ出力を、 logging モジュールに 置き換えます。 違いは:

  • ログレベル(DEBUG/INFO/WARNING/ERROR) で「本番では INFO 以上だけ」 のような切り替え
  • フォーマットを一括変更できる (時刻、 モジュール名、 など)
  • 出力先を stdout / ファイル / ネットワークに切り替えられる
import json, logging, sys, time

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": time.strftime("%Y-%m-%dT%H:%M:%S%z", time.localtime(record.created)),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
        }
        if record.exc_info:
            payload["exc"] = self.formatException(record.exc_info)
        for k, v in record.__dict__.items():
            if k.startswith("ctx_"):
                payload[k[4:]] = v
        return json.dumps(payload, ensure_ascii=False)

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(JsonFormatter())
root = logging.getLogger()
root.addHandler(handler)
root.setLevel(logging.INFO)

log = logging.getLogger("gacha")
log.info("server boot", extra={"ctx_port": 8000})

extra={"ctx_xxx": ...} で 1 ログに付帯情報を載せる。 ctx_ プレフィックスは アプリ独自の慣習で、 フォーマッタが拾って JSON のトップレベルに展開する。

15.2 アクセスログ

全リクエストの「method, path, status, ms」 を 1 行 JSON で出すと、 jq や Datadog で集計しやすくなります。 BaseHTTPRequestHandler の log_message をオーバーライドする手もありますが、 _dispatch の周りに ラップするほうが情報を載せやすい: 

def _dispatch(self, method):
    started = time.perf_counter()
    path = urlparse(self.path).path
    handler = ROUTES.get((method, path))
    status = 200
    try:
        if handler is None:
            status = 404
            return self._json(404, {"error": "Not Found", "path": path})
        try:
            handler(self)
        except AppError as e:
            status = e.status
            self._json(e.status, {"error": e.message})
        except Exception as e:
            status = 500
            log.exception("unhandled", extra={"ctx_path": path})
            self._json(500, {"error": "internal server error"})
    finally:
        log.info("access", extra={
            "ctx_method": method,
            "ctx_path":   path,
            "ctx_status": status,
            "ctx_ms":     round((time.perf_counter() - started) * 1000, 2),
        })

「成功/失敗どちらでも 1 行出る」のがコツ。 try / finally で必ず最後に流す。

15.3 遅いクエリを Postgres 側で検出する

サーバ側のログで「全リクエストの ms」 を見ると、 大体は速いが時々遅い、 が見えてくる。 犯人は SQL のことが多い。 Postgres には「N ミリ秒以上のクエリを自動で吐き出す」 機能が標準で備わっています。 

-- postgresql.conf  または ALTER SYSTEM
ALTER SYSTEM SET log_min_duration_statement = '200ms';

-- auto_explain 拡張をロード
ALTER SYSTEM SET shared_preload_libraries = 'auto_explain';
ALTER SYSTEM SET auto_explain.log_min_duration = '200ms';
ALTER SYSTEM SET auto_explain.log_analyze = on;
ALTER SYSTEM SET auto_explain.log_buffers = on;
SELECT pg_reload_conf();

これで「200ms を超えた SQL は実行計画付きで Postgres ログに出る」 状態。 アプリ側の ログと突き合わせれば「どのリクエストの中で何の SQL が遅かったか」 が追える。

15.4 メトリクスエンドポイント

Prometheus に拾わせるには「テキストで状態を返すエンドポイント」 を 1 つ生やすだけ。 正式には prometheus_client を使うが、 学習目的なら手書きでも 30 行で書ける: 

from collections import Counter

_metrics = {
    "requests_total":     Counter(),
    "request_seconds":    [],
}

def record_request(method, path, status, ms):
    _metrics["requests_total"][(method, path, status)] += 1
    _metrics["request_seconds"].append(ms / 1000)

@route("GET", "/api/metrics")
def metrics(h):
    lines = ["# TYPE gacha_requests_total counter"]
    for (m, p, s), n in _metrics["requests_total"].items():
        lines.append(f'gacha_requests_total{{method="{m}",path="{p}",status="{s}"}} {n}')
    lines.append("# TYPE gacha_request_seconds_sum gauge")
    lines.append(f'gacha_request_seconds_sum {sum(_metrics["request_seconds"]):.6f}')
    body = ("\n".join(lines) + "\n").encode("utf-8")
    h.send_response(200)
    h.send_header("Content-Type", "text/plain; version=0.0.4")
    h.send_header("Content-Length", str(len(body)))
    h.end_headers()
    h.wfile.write(body)

実装は単純ですが、 プロセス再起動でリセットされることに注意。 Prometheus 側は「1 分前と比べて差分」 を見る前提で動くので、 アプリ側は 累計の大きい数を出すだけでよい。

15.5 readiness probe

/api/health は「サーバプロセスは生きている」 を返すだけ。 でも DB が落ちていたら 実用上はサービスとして死んでいる。 そこで「依存先まで含めて健康か」 を返す /api/ready を別途作ります: 

@route("GET", "/api/ready")
def ready(h):
    try:
        with get_conn() as conn, conn.cursor() as cur:
            cur.execute("SELECT 1")
        h._json(200, {"status": "ready"})
    except Exception as e:
        log.warning("not ready", extra={"ctx_err": str(e)})
        h._json(503, {"status": "not ready", "detail": str(e)})

Kubernetes / ECS では /api/health を liveness probe、 /api/ready を readiness probe に紐付ける。 readiness が 503 を返している間はロードバランサから外れるので、 「DB 起動待ちの間にトラフィックを流さない」 が実現できる。

15.6 ダッシュボードを作るとき

Prometheus + Grafana を入れたら、 最初に貼るパネルは:

  • RPS (リクエスト数 / 秒) を method, path で積み上げ
  • p50/p95/p99 レスポンスタイム (heatmap が見やすい)
  • 4xx, 5xx のエラーレート
  • DB 接続エラー率 (ready probe の 503 を別グラフ)

「RED メソッド」(Rate, Errors, Duration) と覚えるとブレない。 これだけ見えていれば異常検知の 8 割はカバーできる。

15.7 落とし穴まとめ

  • print 仕分けは負債。 ログレベルとフォーマットを最初から仕込む
  • アクセスログは必ず try/finally で全リクエスト分出す
  • 遅いクエリ追跡はアプリ側ログ + auto_explain 両輪
  • /api/health と /api/ready は別物。 役割を混ぜない
  • メトリクスはプロセス再起動でリセットされる前提で運用する
