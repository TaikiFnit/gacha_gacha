第 10 章 — 拡張: ここから先

Ch.1 から Ch.8 まで通すと、 ガチャを引いて Box に貯めるだけの 「最小だが本物のゲームバックエンド」が手元に残ります。 ここから先は、 自分が遊びたいゲーム性を足していく、 完全にあなた自身のプロジェクトです。 この章では「次にどこを膨らませるか」 のメニューと、 その実装で必要になりそうなテーブル拡張・SQL パターンを置いておきます。

📐 拡張のスタンス

「全部一気に作る」 ではなく 1 機能 = 1 ブランチ。 今までやってきたステップ式 (動かす → 試す → 拡張する) を継続。 Ch.8 で書いた smoke テストが、 機能追加で既存が壊れないかを守ります。

9.1 ログインボーナス (デイリー報酬)

毎日 1 回、 ログインすると 200 coin もらえる、 みたいな仕組み。 ガチャを長く遊ばせる定番。

必要なもの

  • テーブル: daily_bonuses (user_id, claimed_on date, amount int) — 1 ユーザー 1 日 1 行
  • UNIQUE 制約: (user_id, claimed_on) ← 二重取得を DB で防ぐ
  • API: POST /api/daily/claim → 既に当日分があれば 400, 無ければ INSERT + UPDATE coins
CREATE TABLE daily_bonuses (
    id          BIGSERIAL    PRIMARY KEY,
    user_id     BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    claimed_on  DATE         NOT NULL DEFAULT (CURRENT_DATE AT TIME ZONE 'Asia/Tokyo')::date,
    amount      INTEGER      NOT NULL,
    UNIQUE (user_id, claimed_on)
);

実装のヒント

@route("POST", "/api/daily/claim")
def claim_daily(h):
    AMOUNT = 200
    with get_conn() as conn:
        user = h.require_user(conn)
        with conn.cursor() as cur:
            try:
                cur.execute(
                    """
                    INSERT INTO daily_bonuses (user_id, amount) VALUES (%s, %s)
                    RETURNING claimed_on
                    """,
                    (user["id"], AMOUNT),
                )
                claimed_on = cur.fetchone()["claimed_on"]
            except psycopg.errors.UniqueViolation:
                raise bad_request("今日のボーナスはもう受け取り済みです")
            cur.execute(
                "UPDATE users SET coins = coins + %s WHERE id = %s RETURNING coins",
                (AMOUNT, user["id"]),
            )
            new_coins = cur.fetchone()["coins"]
    h._json(200, {"amount": AMOUNT, "claimed_on": claimed_on, "coins": new_coins})

UNIQUE 制約に守ってもらう のがミソ。 アプリ側で「今日のレコードある?」 を SELECT してから INSERT すると、 ほぼ同時に 2 リクエスト来たときに両方通ってしまう (TOCTTOU バグ)。 INSERT 一発+ UNIQUE で物理的に 1 行にしておけば、 DB が二重を必ず弾く。

9.2 アイドル風コイン自動生成

クッキークリッカー的な要素。 「装備しているキャラ × そのレア度 × 経過秒」 で coins が貯まる。

テーブル拡張

ALTER TABLE users ADD COLUMN last_collected_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
-- equipping = ユーザーが装備しているキャラ (複数可)
CREATE TABLE equipped_characters (
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    character_id BIGINT NOT NULL REFERENCES characters(id) ON DELETE RESTRICT,
    PRIMARY KEY (user_id, character_id)
);

実装のヒント

pull / box / me 等のエンドポイントで、 アクセスのたびに「last_collected_at から 今までで何 coin 貯まったか」 を計算して足す関数 collect(user_id) を呼ぶ。 これだけで「ログインしてないときも貯まっている」 体験ができる (サーバ側で時刻差から逆算)。 

def collect(conn, user_id):
    """前回回収から今までの分を加算する。 アイドル風自動生成。"""
    with conn.cursor() as cur:
        cur.execute(
            """
            SELECT u.coins, u.last_collected_at,
                   COALESCE(SUM(c.rarity), 0) AS rate
              FROM users u
              LEFT JOIN equipped_characters ec ON ec.user_id = u.id
              LEFT JOIN characters c ON c.id = ec.character_id
             WHERE u.id = %s
             GROUP BY u.id
             FOR UPDATE OF u
            """,
            (user_id,),
        )
        row = cur.fetchone()
        elapsed = (datetime.now(timezone.utc) - row["last_collected_at"]).total_seconds()
        gained  = int(elapsed * row["rate"])     # rarity 合計 = 1 秒あたりの取得 coin
        if gained > 0:
            cur.execute(
                "UPDATE users SET coins = coins + %s, last_collected_at = NOW() "
                "WHERE id = %s",
                (gained, user_id),
            )

9.3 ピックアップガチャ (期間限定 weight)

「今週末は SSR ドラゴンが 3 倍出やすい!」 みたいな仕組み。 期間付きの weight オーバーライドテーブルを足すと、 既存の gacha_items を変えずに足せます。 

CREATE TABLE pickup_periods (
    id        BIGSERIAL PRIMARY KEY,
    gacha_id  BIGINT    NOT NULL REFERENCES gachas(id) ON DELETE CASCADE,
    period    TSTZRANGE NOT NULL,   -- ← 範囲型 (PG 機能)
    weights   JSONB     NOT NULL    -- {"10": 6, "11": 6} (character_id → 増加倍率)
);
CREATE INDEX idx_pickup_active ON pickup_periods USING GIST (gacha_id, period);

fetch_pool で NOW() <@ period な行を JOIN して weight を掛け算で適用すると、 既存抽選ロジックは変えずに「期間限定強化」 が実現します。 マスタは過去データを書き換えず、 期間付きで重ねる のが運用の鉄則。

9.4 ランキング / SNS 機能

  • 所持品ランキング: SELECT user_id, COUNT(*) FROM user_characters GROUP BY user_id ORDER BY 2 DESC LIMIT 50
  • レア度別コンプ率ランキング: 5 ★ をいくつ持っているか
  • フレンド機能: friendships(user_a, user_b) で多対多を表現

SNS 系を入れると「他人のデータを参照する」 = アクセス制御の話になります。 自分の Box は自分だけが書き換えられて、 他人からは「公開設定の所持数」 だけ見える、 のような切り分けが必要。 「DB 行 vs 認証ユーザー」 のマッピング をきちんと考える練習になります。

9.5 マイグレーション (本番のスキーマ更新)

ここまでスキーマは「最初に schema.sql を 1 回流すだけ」 で済んでいました。 でも実運用ではテーブルが後から増えたり、 カラムが増えたりします。 そのときに 本番の既存データを残しながらスキーマを変える必要が出ます。

  • 素朴な手法: db/migrations/0001_initial.sql, 0002_daily_bonus.sql ... と番号順 SQL を増やし、 適用済み番号を schema_migrations テーブルで管理
  • 定番ツール: Alembic (SQLAlchemy 系)、 migrate (Go 製、 純 SQL)
  • 原則: 「既存行を壊さない順で変える」 = 列追加 (default 付き) → アプリ更新 → 列の制約強化、 みたいな段階デプロイ

9.6 監視・ログ・運用

  • アクセスログを logging モジュールで構造化 (JSON) して、 sysout/file に
  • 遅いクエリの検出: PG の auto_explain 拡張 + log_min_duration_statement
  • メトリクス: /api/metrics エンドポイントで Prometheus 互換テキストを返す
  • ヘルスチェック: /api/health は既にあるが、 DB 接続まで含めた readiness を別ルートで

9.7 フロントの本気化

学習モード版フロントは「サーバの素の応答が見える」 のが特徴ですが、 本物のゲームにするなら:

  • React / Vue / Svelte で組み直し、 状態管理を整理
  • WebSocket か SSE で「他のユーザーがガチャを引いた」 をリアルタイム通知
  • アニメーション (ガチャ演出、 レア確定エフェクト)
  • モバイル対応の見直し

ただしサーバ側の API 仕様は変えない ことが大事。 現在の web/ も、 新しいフロントも、 同じ /api/* を叩くだけで動く = API がきちんと「契約」 として機能している証。

9.8 学習の旅の終わり、 そして始まり

ここまで通ったあなたは、 もう 「Web バックエンド + RDB がどう動いているか」 をフレームワーク無しで 自分の手で組み上げた経験を持っています。

  • HTTP の中身が見える
  • SQL を直接書ける
  • パスワード/セッションを実装できる
  • 並行性 (FOR UPDATE / トランザクション) がわかる
  • テストを 2 種類 (smoke, unit) 書ける

この後 Django や FastAPI を触ると、 「あぁ、 これは ROUTES 辞書を綺麗に書いただけ」 「これは get_conn() の上に ORM が乗っただけ」と、 全部透けて見えます。 フレームワークを使うかどうか は道具選びの話で、 もう怖くない。

ガチャを伸ばすも良し、 全く別のサービスに応用するも良し。 この教材は完。 でも、 あなたのサーバはここからが本番です。
