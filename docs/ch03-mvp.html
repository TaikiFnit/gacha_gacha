第 3 章 — サーバと DB を繋ぐ最初の成功体験 (MVP)

Ch.1 で HTTP サーバ、 Ch.2 で users テーブルを作りました。 それぞれ別々に動かせるけど、 まだ繋がっていない。 この章で初めて 1 つのシステムになります。

ゴールはシンプル。 REST クライアント (Postman など) からサーバに POST してユーザーを 1 件作り、 ブラウザでサーバの GET を叩くと DB に保存されたユーザーが JSON で返ってくる。 この 1 往復が成立した瞬間が、 本教材で最初の「動くものを自分で作った」 体験です。

📐 この章で学ぶこと
  • Colab で立てたサーバを外から叩く方法 (port を公開する Colab の機能)
  • サーバから同じ Colab 上の sqlite ファイルに INSERT / SELECT する
  • REST クライアントで POST、 ブラウザで GET を試して動くものを確かめる
📝 まだ扱わないこと
  • パスワード / 認証 (Ch.6 で導入)
  • SQL インジェクション対策 ( ? プレースホルダは使うが、 「なぜ」 の話は Ch.5)
  • JOIN / GROUP BY / トランザクション (必要になる Ch.7 / Ch.8 で)
  • 本格フロントエンド (Ch.4 でローカルに移ってから)

MVP は「動く」 を最優先。 セキュリティや効率の話は、 必要性が見えてから足していきます。

3.1 これから作るシステム

Ch.4 以降ではこの構成のまま規模を大きくしていきます。 REST クライアントは本物のフロント (web/) になり、 SQLite は PostgreSQL に置き換わり、 サーバは認証や抽選など本気の処理を持つようになります。 でも骨格はこれと同じ。

3.2 REST クライアントを 1 つ用意する

ブラウザは GET なら URL を打てば叩けますが、 POST はそうはいきません。 何かAPI テスト用のツールが必要です。 好きなものを 1 つ選んでください:

ツール場所登録備考
Hoppscotch Web ブラウザ 不要 一番おすすめ。 開いた瞬間使える
Postman デスクトップアプリ 無料アカウント要 業界標準。 機能豊富
Insomnia デスクトップアプリ 不要 (基本機能) シンプルでよい
!curl Colab セル内 不要 シェル混在。 セルで完結する

この章では Hoppscotch を念頭に書きますが、 どれを使っても操作は同じ (URL、 メソッド、 ヘッダ、 ボディを設定して送るだけ)。

3.4 サーバを起動する (Ch.1 の最終形 = セル 1-G)

Ch.1 で育てた最終のサーバを起動します。 新しいセルを 1 つ作って、 Ch.1 のセル 1-A (serve/hit ヘルパ) → セル 1-G (例外を JSON エラー化した完成形) の順にコピペしてください。 1-G まで動くと、 ルータ + 例外ハンドリング付きのサーバが port 8000 で立ちます。

3.5 Spiral 1 — Colab の port を公開して、 ブラウザから叩く

これまで Colab 内部からしか叩いていなかったサーバを、 外部から叩けるようにします。 Colab には serve_kernel_port_as_public という関数が用意されていて、 ローカルで動いているポートに対する公開 URL を発行してくれます。

📒 セル 3-B — 公開 URL を取得 
from google.colab.output import serve_kernel_port_as_public
PUBLIC_URL = serve_kernel_port_as_public(8000)
print("公開URL:", PUBLIC_URL)
✅ 期待される出力 (毎回違う URL が出る) 
公開URL: https://abcd1234.colab.googleusercontent.com/

🧪 ブラウザで GET を叩く

表示された URL の末尾に api/health を付けて、 ブラウザの新しいタブで開いてみてください。 例: https://abcd1234.colab.googleusercontent.com/api/health

最初に Colab の認可画面 (「公開を許可しますか?」 の確認) が出ます。 「許可」 を押すと、 {"status": "ok"} がブラウザに表示されます。 これが、 サーバが Colab の中から飛び出して外の世界と話した最初の瞬間。

📝 公開 URL の有効期限 この URL は Colab セッションが続いている間だけ有効です。 ランタイムを切ると消える。 別の人と共有して同時に叩くこともできるので、 友達とローカルではなくこの URL を使って ペアで作業すると面白い。

3.6 Spiral 2 — POST を受け取って中身を覗く

まず「受け取った body をそのまま print する」 だけのハンドラを足します。 DB に書く前に、 「サーバまでデータが来ているか」 を 1 度確かめるのが今回のスパイラル。

📒 セル 3-C — POST /api/users (echo 版) を追加

def create_user(h):
    body = h._read_json()
    print("👀 受信:", body)        # ← Colab セル下に出力される
    h._json(200, {"received": body})

3.7 Spiral 3 — DB に INSERT する

届いたデータを sqlite に保存します。 Ch.2 で作った gacha.db に sqlite3 モジュール経由で接続し、 INSERT を発行。

📒 セル 3-D — sqlite 接続ヘルパ 
import sqlite3
from contextlib import contextmanager

DB_PATH = "gacha.db"  # Ch.2 で %%sql sqlite:///gacha.db に作ったファイル

@contextmanager
def get_conn():
    """1 リクエスト分の DB 接続を貸す。 ブロックを抜けるときに自動コミット。"""
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row    # 結果を辞書ライクにアクセスできる
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()

# 接続確認
with get_conn() as conn:
    cur = conn.execute("SELECT COUNT(*) AS n FROM users")
    print("現在のユーザー数:", cur.fetchone()["n"])
📒 セル 3-E — POST /api/users を本当に INSERT する 
@route("POST", "/api/users")
def create_user(h):
    body = h._read_json()
    name = (body.get("name") or "").strip()
    display_name = (body.get("display_name") or name).strip()
    if not name:
        raise bad_request("name は必須")

    with get_conn() as conn:
        cur = conn.execute(
            # ?  はプレースホルダ。 文字列を直接埋め込まないこと (Ch.5 で詳しく)
            "INSERT INTO users (name, display_name) VALUES (?, ?) "
            "RETURNING id, name, display_name, created_at",
            (name, display_name),
        )
        row = dict(cur.fetchone())

    h._json(200, {"user": row})

serve(App)
print("✅ /api/users が DB に INSERT するようになった")

3.8 Spiral 4 — GET でユーザー一覧を返す

最後の往復。 ブラウザで GET を叩くと DB の中身が JSON で返ってくる ようにします。

📒 セル 3-F — GET /api/users 
@route("GET", "/api/users")
def list_users(h):
    with get_conn() as conn:
        rows = conn.execute(
            "SELECT id, name, display_name, created_at FROM users ORDER BY id"
        ).fetchall()
    h._json(200, {"users": [dict(r) for r in rows]})

serve(App)

🧪 ブラウザで叩く

{PUBLIC_URL}/api/users をブラウザの新タブで開きます (Spiral 1 で取った公開 URL)。 ブラウザは GET を叩くだけなら何も特別なツール不要。

🎉 期待される表示 
{
  "users": [
    {"id": 1, "name": "alice", "display_name": "アリス", "created_at": "2026-04-27 06:30:12"},
    {"id": 2, "name": "bob",   "display_name": "ボブ",   "created_at": "2026-04-27 06:32:55"}

これがゴール。 別マシンの REST クライアントから POST → サーバ → Colab の SQLite に保存 → ブラウザの GET → 同じ DB から読み出し → JSON 表示。 君がここまで自分の手で組み上げた「動くシステム」です。

3.9 ここまでで気づくこと

SQL を打たないと中身が見えるのは psql / %%sql の方が便利

ブラウザで /api/users を見るのと、 Colab で %%sql SELECT * FROM users を打つのと、 同じデータが見えました。 違いは:

  • API 経由: ネットワーク越し、 認証や絞り込みなどビジネスロジックを通る経路
  • SQL 直接: DB に直接アクセス。 開発者がデバッグや管理に使う経路

実運用では SQL 直接アクセスは「サーバ管理者だけ」 で、 一般ユーザーには API 経由しか触らせません。 しかし開発中はこの 2 つを両方見ることが、 動作を理解する一番の近道です。

「同じテーブル、 同じデータ」 を 2 つの世界が共有している

Ch.2 で %%sql から作ったテーブルに、 Ch.3 の Python コードが INSERT しています。 DB は共有資源。 サーバを止めても DB は残るし、 サーバを再起動しても以前のデータは見える (Spiral 4 で確認)。 これが永続化のありがたみ。

3.10 まだ抱えている問題 — 次章への動機

  • 同じ name で 2 回 POST すると 500 が出る (= ちゃんと 400 に変換したい)
  • ブラウザで /api/users を直接見られる = 認証無しで誰でも全ユーザー一覧が読める
  • Colab を閉じるとサーバも DB も消える (= ローカルに移したい / Postgres にしたい)
  • 本物の「ガチャ画面」 が無い。 REST クライアントで叩くのは開発体験で、 ゲーム体験ではない

これを解いていくのが Ch.4 以降。 次の Ch.4 でローカルに環境を移行して、 Postgres + 本格フロント (web/) を導入します。
