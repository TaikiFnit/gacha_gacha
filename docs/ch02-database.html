Chapter 2 所要時間: 90〜120 分 形式: Docker で Postgres を立て、 psql で 1 テーブルを動かす

第 2 章 — Postgres + Docker でデータベース基礎

この章では本物のリレーショナルデータベース PostgreSQL を、 Docker コンテナとして起動して、 psql という対話的シェルから SQL を打ちます。 ガチャシステム全体で必要な 5 つのテーブルのうち、 1 つだけ (users テーブル) を作るのが この章のゴール。 残りは Ch.5 でまとめて作ります。

この章を通過すると、 「Postgres コンテナを起動して、 psql に入って、 CREATE/INSERT/SELECT で データを操作する」 一連の動作が手に馴染みます。 これが本教材を通じて使う土台になります。

📝 なぜいきなり Postgres + Docker?

SQLite で導入する選択肢もありますが、 教材としては本番でも使う Postgres を最初から触る 方を選びました。 理由:

  • 「学習用 DB」 と「本番 DB」 でハマる場所が違う (型、 ロック、 トランザクション)。 結局 後で Postgres 固有の話を別途やる必要が出る
  • Docker は Web 開発の現場で必須スキル。 「とりあえず動かす」 を 1 度経験しておくと後が楽
  • SQL の文法面では SQLite と Postgres で大半が共通。 違うところは出てきたときにコラムで触れる

2.1 Postgres コンテナを起動する

docker-compose.yml を書く

作業フォルダの直下に docker-compose.yml を作ります。 これは「どんな Docker コンテナを、 どんな設定で立てるか」 を 宣言するファイルです。

📝 docker-compose.yml — 学習用 Postgres 設定 
# docker-compose.yml
# 学習用 Postgres コンテナ。
#   docker compose up -d   で起動
#   docker compose down    で停止
#   docker compose down -v で完全リセット (ボリュームごと削除)
services:
  db:
    image: postgres:16
    container_name: gacha_pg
    restart: unless-stopped
    environment:
      POSTGRES_DB: gacha
      POSTGRES_USER: gacha
      POSTGRES_PASSWORD: gacha
      TZ: Asia/Tokyo
    ports:
      - "5432:5432"
    volumes:
      # コンテナを止めてもデータが残るよう、 ホスト側のボリュームに保存
      - gacha_pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U gacha -d gacha"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  gacha_pgdata:

📚 コラム: docker compose up -d で何が起きているか
  • image: postgres:16 — Docker Hub から PostgreSQL バージョン 16 のイメージを引っ張ってくる (初回は数分かかる)
  • container_name — 起動するコンテナの名前。 後で docker exec gacha_pg ... として使う
  • environment — Postgres 公式イメージの初期化に使う環境変数。 この 3 つで「データベース名 / ユーザー / パスワード」 が決まる
  • ports: "5432:5432" — ホスト側 (= あなたの Windows PC) の 5432 番を、 コンテナ内の Postgres の 5432 番に転送する。 これで Python から localhost:5432 で繋げる
  • volumes: gacha_pgdata:... — コンテナを止めてもデータを失わないよう、 Postgres のデータ領域 (/var/lib/postgresql/data) を Docker 管理の名前付きボリュームに保存
⚠️ ポート 5432 の衝突

もし起動時に port is already allocated や bind: An attempt was made to access a socket... のようなエラーが出たら、 Windows で別の Postgres (例: ローカルにインストール済みの PG) が 5432 を使っています。 解決策:

  • 使っていなければ Windows サービスから止める (タスクマネージャ → サービス → postgresql-x64-XX を停止)
  • 残しておきたいなら docker-compose.yml の ports を "5433:5432" に変えて、 この教材では 5433 で繋ぐ

占有プロセスを調べたい場合: Get-NetTCPConnection -LocalPort 5432 で確認できます。

psql に入って Postgres と話す

Postgres は起動しました。 これに接続する一番素直な方法が、 Postgres 公式の対話的シェル psql です。 Docker コンテナの中に psql は同梱されているので、 docker exec でコンテナの中に入って実行します。

▶️ psql に入る 
# docker exec で、 動いている gacha_pg コンテナの中に入って psql を起動
docker exec -it gacha_pg psql -U gacha -d gacha

# プロンプトが gacha=# に変わる。 ここからは SQL を打てる
# 抜けるときは \q (バックスラッシュ + q)
✅ 期待される出力 
psql (16.x)
Type "help" for help.

gacha=#
📚 コラム: psql のメタコマンド (バックスラッシュ系)

psql プロンプトでは、 SQL の他に メタコマンド という psql 専用の命令が使えます。 全部 \ (バックスラッシュ) で始まります。

メタコマンド意味
\lデータベース一覧
\dt現 DB のテーブル一覧
\d usersusers テーブルの構造を表示
\dnスキーマ一覧
\duユーザー (ロール) 一覧
\qpsql を終了
\?メタコマンド一覧
\h SELECTSQL 文 (例: SELECT) のヘルプ

\dt で「いま何のテーブルがあるか」、 \d テーブル名 で 「そのテーブルの列と型と制約は?」 を確認するのが基本ルーチンです。

2.2 リレーション / テーブル — 厳密にいうと

よく「テーブルは 2 次元の表」 と教わりますが、 リレーショナルモデルの定義は少し違います。

📚 ちゃんとした定義

リレーション (relation) は、 ある属性の集合に対する タプルの集合 (set)です。 集合なので:

  • 行に重複は無い (同じタプルは 1 個まで)
  • 行に順序は無い (上から読んでも下から読んでも意味は同じ)
  • 列にも順序は無い (列名でアクセスする)

SQL の世界の テーブル (table) はこのリレーションを実装した「近い親戚」 で、 厳密には少し違います:

  • 主キーが無いと行の重複が起き得る
  • 列に物理的な並び順がある (が、 アプリ側で頼ってはいけない)

本教材では「テーブル = リレーションの実用形」 として扱います。 実装上は 2 次元の表として描けるが、 概念は集合と覚えておけば十分です。

2.3 主キー (Primary Key, PK) を腹に落とす

リレーションの中で「その行を世界で 1 つだけ特定する列 (もしくは列の組み合わせ)」 を主キーと呼びます。 ユーザーで言えば「id = 1 ならアリス、 id = 2 ならボブ、 同じ id を持つ別人はいない」 のような。

主キーの 3 つの不変条件

  1. 一意性: 同じ値の行が 2 つあってはならない
  2. 非 NULL: 「未定」 を許さない (= 値がなければそもそも識別できない)
  3. 不変性 (運用上): 一度決めた値は変えない (他のテーブルから参照されているため)

自然キー vs 代替キー

  • 自然キー: 業務上意味のある値そのまま (例: メールアドレス、 マイナンバー)
  • 代替キー (サロゲートキー): DB が自動で振る連番 (例: id INTEGER GENERATED BY DEFAULT AS IDENTITY)

本教材では 代替キー (= 自動採番の id 列) を主キーにします。 業務的な意味 (メアド変更、 名前変更) を主キーが背負わなくて済むので運用が楽。

2.4 users テーブルを作る (CREATE TABLE)

2.6 制約 — 「変な値」 を DB が弾く

SQL の真価は「データの整合性を DB が守ってくれる」 ところにあります。 具体的には CREATE TABLE で書いた制約 (constraint) が、 不正な INSERT/UPDATE を弾きます。 実際に弾かれる様子を見てみます。

📒 SQL 6 — UNIQUE 違反 
-- name = 'alice' は既に存在する → UNIQUE 違反
INSERT INTO users (name, display_name) VALUES ('alice', '別人だよ');
✅ 期待される出力 (失敗するのが正解) 
ERROR:  duplicate key value violates unique constraint "users_name_key"
DETAIL:  Key (name)=(alice) already exists.

この duplicate key value violates unique constraint こそが、 第 7 章で POST /api/register の重複登録を防ぐ最後の防波堤になります。 アプリ側でも事前に SELECT 1 FROM users WHERE name = ... で重複チェックして ユーザーに分かりやすいエラーメッセージを返しますが、 同時に同じ name で 2 件登録された場合 (= 競合) は 事前チェックだけでは防げません。 そこで、 DB が UNIQUE 違反として弾くことで 「データの一意性」 だけは絶対に守れる、 という二段構えにします。

📚 コラム: 「アプリで書く」 vs 「DB が守る」

どちらも書きます。 役割が違うだけです:

  • アプリ側のバリデーション: ユーザー体験のため (分かりやすいメッセージ、 早く返す)
  • DB 制約: データ整合性のため (競合・バグ・直接 SQL 実行など、 アプリを通らない経路でも守る)

Ch.7 の register 実装では、 事前に SELECT で確認しつつ、 最終的な INSERT では UNIQUE 違反 (psycopg.errors.UniqueViolation) も拾える形にして、 競合時にも 400 を返せるようにします。

📒 SQL 7 — NOT NULL 違反 
INSERT INTO users (name) VALUES ('mallory');   -- display_name を欠落させる
✅ 期待される出力 
ERROR:  null value in column "display_name" of relation "users" violates not-null constraint
DETAIL:  Failing row contains (..., mallory, null, ...).
📒 SQL 8 — CHECK 制約を試す 
-- 後の章で使う coins 列に CHECK (coins >= 0) を付けるのと同じ趣旨
-- ここでは ALTER TABLE で users に試しに足してみる

ALTER TABLE users
  ADD COLUMN age INTEGER CHECK (age >= 0 AND age < 150);

INSERT INTO users (name, display_name, age) VALUES ('mallory', 'マロリー', 999);
✅ 期待される出力 
ALTER TABLE
ERROR:  new row for relation "users" violates check constraint "users_age_check"
DETAIL:  Failing row contains (..., 999).

999 歳のユーザーを作ろうとすると DB が弾いてくれました。 同様に、 文字列長 / 範囲 / 列同士の関係 (CHECK (start_at < end_at)) など、 「アプリ側のバリデーションで言いたい論理」 を DB に書いておくと、 どの経路でデータが入っても安全に守られます。

動作確認できたので、 試した age 列は片付けておきます (この後使わない):

📒 SQL 9 — age 列を消す 
ALTER TABLE users DROP COLUMN age;
\d users
📚 コラム: 外部キー (Foreign Key, FK) — 次章以降で活躍

Ch.5 で gacha_items.gacha_id や user_characters.user_id のような 参照関係を作るときに FK 制約が登場します。 こんな書き方: 

CREATE TABLE user_characters (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    character_id BIGINT NOT NULL REFERENCES characters(id) ON DELETE RESTRICT,
    obtained_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
  • REFERENCES users(id) = この列の値は users.id に 存在する値でなければならない、 という制約
  • ON DELETE CASCADE = 親 (users) を消したら子 (user_characters) も 連鎖して消える
  • ON DELETE RESTRICT = 子 (user_characters) で参照されている 親 (characters) を消そうとするとエラーで止める

FK は「孤立した子データ」 (= 親が存在しない参照) を DB レベルで防ぐためのもの。 Ch.5 で実際に登場します。

2.7 持ち帰る — db/schema.sql に保存

ここまで psql で打ってきた DDL (= テーブル定義) を、 ファイルとして残すのが 重要なステップです。 このファイルがあれば、 別 PC でも、 数ヶ月後でも、 同じスキーマを再現できます。

作業フォルダに db/ ディレクトリを作って、 schema.sql を保存します。 psql から抜けて (\q)、 PowerShell に戻ってから:

📝 db/schema.sql — 「再現可能なスキーマ定義」 
-- db/schema.sql
-- ガチャシステムの DB スキーマ。 docker-entrypoint-initdb.d/ にマウントすれば
-- コンテナ初回起動時に自動で実行される。

CREATE TABLE IF NOT EXISTS users (
    id           BIGSERIAL    PRIMARY KEY,
    name         TEXT         NOT NULL UNIQUE,
    display_name TEXT         NOT NULL,
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
-- (Ch.5 でキャラ・ガチャ・所持履歴の 4 テーブルを足していく)
📝 docker-compose.yml — schema.sql をマウントする 
# docker-compose.yml に volumes を 1 行追加
services:
  db:
    image: postgres:16
    container_name: gacha_pg
    # ... 中略 ...
    volumes:
      - gacha_pgdata:/var/lib/postgresql/data
      # 👇 これを追加。 コンテナ初回起動時に自動で実行される
      - ./db/schema.sql:/docker-entrypoint-initdb.d/01_schema.sql:ro

これで「コンテナを完全リセットしても、 schema.sql から再生成される」 状態になりました。 「データは消えるが、 構造は再現できる」 のが大事です。

▶️ 完全リセットして再生成を確認 
# データボリュームごと削除
docker compose down -v

# 再起動 (このタイミングで schema.sql が走る)
docker compose up -d

# psql に入って users テーブルが既にあることを確認
docker exec -it gacha_pg psql -U gacha -d gacha -c "\dt"
✅ 期待される出力 
         List of relations
 Schema | Name  | Type  | Owner
--------+-------+-------+--------
 public | users | table | gacha
(1 row)
📝 docker-entrypoint-initdb.d の挙動
  • このディレクトリにマウントされた .sql / .sh ファイルは、 コンテナの初回起動時 (= データボリュームが空のとき) だけ実行される
  • docker compose down (-v なし) → up -d ではボリュームが残るので再実行されない
  • schema.sql を変えて反映したい場合は docker compose down -v でボリュームごと消すか、 手動で docker exec ... psql ... -f schema.sql で流し直す

2.8 GUI で覗きたいとき (任意)

psql は強力ですがコマンドライン。 「もっと視覚的に見たい」 場合は GUI クライアントが便利です。 推奨は次の 2 つ (どちらも無料):

  • DBeaver — 多 DB 対応、 高機能。 教材中ずっと使える
  • pgAdmin — Postgres 公式、 機能豊富
  • VS Code の SQLTools 拡張 — エディタの中で軽く使うのに便利

接続情報はすべて同じ: 

Host:     127.0.0.1
Port:     5432       (docker-compose.yml で 5433 に変えていた場合は 5433)
Database: gacha
User:     gacha
Password: gacha

本章のまとめ

  • Postgres は Docker コンテナで docker compose up -d 一発で立つ。 データはボリュームで永続化
  • psql は docker exec -it gacha_pg psql -U gacha -d gacha で入れる。 抜けるのは \q
  • SQL の基本 4 操作: CREATE / INSERT / SELECT / UPDATE / DELETE。 セミコロンで区切る。 UPDATE/DELETE は WHERE 必須
  • 制約 (NOT NULL / UNIQUE / CHECK / FK) は DB が守る最後の防波堤。 アプリ側のバリデーションと組み合わせて二段構えにする
  • 主キーは「行を世界で一意に特定」 する列。 自動採番 (BIGSERIAL) を使うのが定番
  • DDL は db/schema.sql としてファイル化、 docker-entrypoint-initdb.d にマウントすれば再現可能
