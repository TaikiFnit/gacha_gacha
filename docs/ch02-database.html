Step 3 — gachas + 多対多の中間テーブル

🎯 課題

「ガチャ筐体」と「キャラ」は多対多。 1 つのガチャに複数のキャラ、1 つのキャラが複数のガチャに登場し得る。 これを RDB で表現する常套手段が 中間テーブル。今回はそこに weight (重み) も持たせる。

📋 仕様

CREATE TABLE gachas (
    id    BIGSERIAL PRIMARY KEY,
    name  TEXT      NOT NULL UNIQUE,
    price INTEGER   NOT NULL CHECK (price > 0)
);

CREATE TABLE gacha_items (
    id           BIGSERIAL PRIMARY KEY,
    gacha_id     BIGINT    NOT NULL REFERENCES gachas(id)     ON DELETE CASCADE,
    character_id BIGINT    NOT NULL REFERENCES characters(id) ON DELETE RESTRICT,
    weight       INTEGER   NOT NULL CHECK (weight > 0),
    UNIQUE (gacha_id, character_id)
);

💡 ヒント

  • 排出設定を一気に入れるなら INSERT ... SELECT: 
    INSERT INTO gacha_items (gacha_id, character_id, weight)
SELECT g.id, c.id,
       CASE c.rarity WHEN 1 THEN 60 WHEN 2 THEN 30 ELSE 10 END
  FROM gachas g, characters c
 WHERE g.name = '通常ガチャ';
  • 排出表は JOIN + ウィンドウ関数で確率付きにする: 
    SELECT c.name, gi.weight,
       round(gi.weight * 100.0 / sum(gi.weight) over (partition by g.id), 2) AS pct
  FROM gacha_items gi JOIN gachas g ON g.id=gi.gacha_id
                       JOIN characters c ON c.id=gi.character_id
 ORDER BY g.id, pct DESC;

📄 答え

exercises/ch02/step3_gachas_and_items.sql

🧪 演習

  • 同じ (gacha_id, character_id) を二重に入れる → UNIQUE違反
  • 存在しない gacha_id を入れる → FK違反
  • DELETE FROM characters WHERE id=1 → ON DELETE RESTRICT で守られる
  • DELETE FROM gachas → ON DELETE CASCADE で gacha_items も消える

Step 4 — user_characters + トランザクション

🎯 課題

ユーザーの所持品を表す user_characters を作る。 ガチャ 1 回引く処理 ( coins -100, 履歴に 1 行 INSERT )を、 トランザクションで束ねて 1 セットで実行する。

📋 仕様

  • 履歴テーブル。1 回引くごとに 1 行 INSERT
  • user_id FK → users (CASCADE)
  • character_id FK → characters (RESTRICT)
  • obtained_at TIMESTAMPTZ DEFAULT NOW()
  • (user_id) に索引を貼る (Box 表示で何度も WHERE される)

💡 ヒント — ガチャ 1 回の SQL

BEGIN;
  -- 二重消費を防ぐため行ロック
  SELECT coins FROM users WHERE name='alice' FOR UPDATE;
  UPDATE users SET coins = coins - 100 WHERE name='alice'
   RETURNING coins;
  INSERT INTO user_characters (user_id, character_id)
  SELECT u.id, c.id
    FROM users u, characters c
   WHERE u.name='alice' AND c.name='スライム'
  RETURNING id, obtained_at;
COMMIT;

Step 5 — JOIN / GROUP BY / ウィンドウ関数で Box を出す

🎯 課題

ここまでで作ったテーブルから、本システムの「Box」(所持キャラ一覧 + 個数) を SQL 1 本で出す。

📋 必要なクエリ

  1. alice の所持キャラ + 個数 (rarity 降順、id 昇順)
  2. 全キャラ + alice の所持数 (LEFT JOIN: 未所持も列挙)
  3. レア度別のコンプ率 (CTE + LEFT JOIN)
  4. 通常ガチャの排出確率 (ウィンドウ関数)

💡 ヒント

  • LEFT JOIN で「無いものは NULL」を作る。COUNT(uc.id) のように非NULLカラムを数えると、未所持キャラが 0 になる
  • CTE は WITH owned AS (...) SELECT ... で書ける
  • 累積確率を出すなら SUM(weight) OVER (ORDER BY weight DESC ROWS UNBOUNDED PRECEDING)

Step 6 — わざと制約に殴られる

🎯 課題

これは正解を実行する演習ではなく、わざと失敗する SQL を打って DB が何を守ってくれているかを言葉にする回。

試すこと

  • NOT NULL: 必須カラムを欠落させて INSERT
  • UNIQUE: 同じ name を 2 回 INSERT
  • CHECK: rarity = 9 / weight = 0 を入れる
  • FK: 存在しない参照先を入れる
  • ON DELETE RESTRICT: 参照されてるキャラを消そうとする
  • ROLLBACK: トランザクションで途中失敗 → 全部巻き戻る

仕上げ確認: 本物のスキーマと比べる

ここまでで作った 5 テーブル + α が、本番の db/schema.sql とほぼ同じ形になっているはずです。 違いは:

  • 本番には sessions テーブルが追加されている (第8章で扱う)
  • 本番には (user_id, character_id) の複合索引もある (検索性能用)
  • 本番では characters の id を seed で手で振ってある (利便性のため)

本章のまとめ

  • テーブルは「同じ事実を 1 箇所だけに」分けて持つ
  • 多対多は中間テーブルで表現する。本気の "うまみ" は重みや状態を中間に持てるところ
  • NOT NULL / UNIQUE / CHECK / FK はアプリコードの代わりにDBが守ってくれる
  • 複数行の更新が一塊なら必ずトランザクション (BEGIN..COMMIT)
  • JOIN / GROUP BY / ウィンドウ関数まで使えると、ビジネスロジックの大半は SQL で書ける
