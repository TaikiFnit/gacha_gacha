第 13 章 — ランキング / SNS 機能

ガチャは「他人と比べる」 と一気に楽しくなります。 所持品ランキング、 フレンド、 公開設定 — この章は 「自分のデータは自分しか書けない、 他人のデータは公開された分だけ見える」 という認可境界の話に踏み込みます。

🎯 この章のゴール
  1. GET /api/ranking/box 所持キャラ数ランキング (上位 50)
  2. GET /api/ranking/comp/:rarity レア度別コンプ率ランキング
  3. friendships 多対多テーブル + 申請/承認フロー
  4. users.public_box フラグで「Box を公開するか」 を本人が選べる
  5. 他人の Box は公開設定が ON のときだけ見える

13.1 所持数ランキング

SELECT u.id, u.name, COUNT(uc.character_id) AS owned
  FROM users u
  LEFT JOIN user_characters uc ON uc.user_id = u.id
 GROUP BY u.id
 ORDER BY owned DESC, u.id ASC
 LIMIT 50;

LEFT JOIN なので所持 0 のユーザーも 0 件として並ぶ。 順位を返したいなら ウィンドウ関数: 

SELECT u.id, u.name, COUNT(uc.character_id) AS owned,
       RANK() OVER (ORDER BY COUNT(uc.character_id) DESC) AS rank
  FROM users u
  LEFT JOIN user_characters uc ON uc.user_id = u.id
 GROUP BY u.id
 ORDER BY rank, u.id
 LIMIT 50;

RANK() は同点を同順位 + 飛び番、 DENSE_RANK() は同点を同順位 + 飛ばさない、 ROW_NUMBER() は完全な通し番号。 サービスの「同率はどう見せたいか」 で選ぶ。

13.2 レア度別コンプ率

「★ 5 を全 X 体中 何体持っているか」 を計算するには、 マスタ側の母数と所持側の分子を 別 SELECT で出して JOIN する: 

WITH total AS (
    SELECT COUNT(*) AS n FROM characters WHERE rarity = 5
),
owned AS (
    SELECT u.id, u.name,
           COUNT(DISTINCT c.id) AS got
      FROM users u
      LEFT JOIN user_characters uc ON uc.user_id = u.id
      LEFT JOIN characters     c   ON c.id = uc.character_id AND c.rarity = 5
     GROUP BY u.id
)
SELECT o.id, o.name, o.got, t.n,
       ROUND(o.got::numeric / NULLIF(t.n, 0) * 100, 1) AS comp_pct
  FROM owned o, total t
 ORDER BY comp_pct DESC NULLS LAST, o.id
 LIMIT 50;

COUNT(DISTINCT c.id) ← 同じキャラを 2 体持っていても重複カウントしない ためのキモ。 NULLIF(t.n, 0) ← マスタが 0 体だったときのゼロ除算を回避。

13.3 フレンド機能

フレンドは多対多 + 自分自身との関係。 申請 / 承認のステートを持たせます: 

CREATE TABLE friendships (
    requester_id BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    addressee_id BIGINT      NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    status       TEXT        NOT NULL CHECK (status IN ('pending', 'accepted', 'blocked')),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (requester_id, addressee_id),
    CHECK (requester_id <> addressee_id)
);

CREATE INDEX idx_friend_addressee ON friendships(addressee_id, status);

設計のポイント

  • 方向あり: A → B の申請と B → A の申請は別レコード。
  • CHECK (requester_id <> addressee_id) ← 自分にフレンド申請できないことを DB で保証。
  • 承認すると status = 'accepted' に更新。 双方向にレコードを増やすかは設計次第 (本教材は 「片方だけ」 + 既存行を UPDATE 方式を採用)。
  • 「フレンド一覧」 を引くときは requester_id = me OR addressee_id = me + status = 'accepted' で UNION 的に出す。

13.4 認可境界 — 他人の Box を覗くには

GET /api/users/:id/box を素朴に書くと、 ログインしていれば誰の Box でも見える = 個人情報がダダ漏れ。 設計として:

  1. users.public_box BOOLEAN NOT NULL DEFAULT FALSE 列を追加
  2. 本人が POST /api/me/public_box で ON/OFF を切替可能
  3. GET /api/users/:id/box は公開フラグが TRUE の時だけ 200 で返す。 FALSE なら 403。
@route("GET", "/api/users/{id}/box")
def view_box(h, id: int):
    with get_conn() as conn:
        viewer = h.require_user(conn)         # 認証は必要
        with conn.cursor() as cur:
            cur.execute(
                "SELECT id, name, public_box FROM users WHERE id = %s",
                (id,),
            )
            target = cur.fetchone()
            if target is None:
                raise not_found()
            # 自分自身は常に見られる。 他人は public_box=TRUE のときだけ
            if target["id"] != viewer["id"] and not target["public_box"]:
                raise forbidden("この Box は非公開です")
            cur.execute(
                "SELECT character_id, COUNT(*) AS n "
                "  FROM user_characters WHERE user_id = %s "
                " GROUP BY character_id ORDER BY character_id",
                (id,),
            )
            box = cur.fetchall()
    h._json(200, {"user": target["name"], "box": box})
⚠️ 「ログイン済 = 全部見える」 は事故の温床

「DB 行 vs 認証ユーザーのマッピング」 を毎エンドポイントで明示的に書く。 「自分のデータか?」 「公開設定はどうか?」を SQL の WHERE か、 その前のガード文で必ず通す。 これが SNS 系機能で一番事故を起こす場所。

13.5 ページネーション

ランキングは TOP 50 だけでも十分ですが、 「次の 50」 を出したくなることがあります。 シンプルなのは LIMIT 50 OFFSET 0/50/100/...。 ただし、 OFFSET は 後ろのページほど遅くなる(全行を読み飛ばす) ので、 数万行を超えるなら keyset pagination (WHERE owned < 最後のowned) に切り替えます。

13.6 落とし穴まとめ

  • COUNT の前に DISTINCT を忘れない (重複所持の罠)
  • 母数ゼロ除算は NULLIF で回避
  • フレンドは方向あり / 自己ループ禁止 / ステート列あり、 を DB で保証
  • 「他人のデータを見せる」 場面では必ず認可チェックを SQL or ガード文で書く
  • OFFSET ベースのページネーションは件数が育つと遅くなる
