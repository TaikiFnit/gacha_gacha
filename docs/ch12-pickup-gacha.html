第 12 章 — ピックアップガチャ (期間限定 weight)

「今週末は SSR ドラゴンが 3 倍出やすい!」 — ソシャゲ運営の定番。 Ch.5 で書いた重み付き乱択ロジックを変えずに、 期間限定の倍率を後付けで重ねる 設計を学びます。 マスタを書き換えないのが運用上の鉄則です。

🎯 この章のゴール
  1. pickup_periods テーブル (TSTZRANGE + JSONB) を追加
  2. fetch_pool を「アクティブな期間限定 weight があれば乗算」 に改造
  3. GIST インデックスで「現在 NOW() に重なる期間」 を高速に取り出す
  4. 期間内 / 期間外で抽選結果の分布が変わるのを観察

実習は exercises/ch12/ の step1〜6 を順に流すだけで動きます。

12.1 何が悩ましいのか

Ch.5 で作った gacha_items (gacha_id, character_id, weight) テーブル。 ここに直接 weight を上書きすれば「このキャラの確率を上げる」 は実現できます。 でもこれをやると:

  • 期間が終わった後、 元の weight に戻す手作業が発生 (戻し忘れる)
  • 過去どの期間にどれだけ盛っていたかの履歴が消える
  • 「同じガチャに対して複数のピックアップが期間重複」 を表現できない

正解は「マスタは絶対に触らず、 期間付きの上乗せテーブルを別に持つ」。

12.2 テーブル設計

CREATE TABLE pickup_periods (
    id        BIGSERIAL PRIMARY KEY,
    gacha_id  BIGINT    NOT NULL REFERENCES gachas(id) ON DELETE CASCADE,
    period    TSTZRANGE NOT NULL,
    weights   JSONB     NOT NULL,
    note      TEXT
);

CREATE INDEX idx_pickup_active
    ON pickup_periods USING GIST (gacha_id, period);

INSERT INTO pickup_periods (gacha_id, period, weights, note) VALUES
  (1,
   tstzrange('2026-04-26 00:00+09', '2026-04-29 00:00+09', '[)'),
   '{"10": 6, "11": 6}',
   'GW 前半 SSR ドラゴン3倍ピックアップ');

設計のポイント

  • TSTZRANGE: PostgreSQL 固有の「タイムゾーン付き時刻範囲型」。 '[)' は「開始は含む、 終了は含まない」 半開区間。
  • JSONB: {"character_id": 倍率} の辞書を 1 列に持つ。 スキーマ変更なしで「対象キャラ何体でも書ける」。
  • GIST インデックス: 範囲型に対する「重なり (&&) / 含む (@>) /含まれる (<@)」 の問い合わせを高速化。 B-Tree では効かない (範囲型は 順序が無い ので)。
  • note 列は運用で「なんのキャンペーンだったっけ」 を残すため。 必須ではないが書くと未来の自分を救う。

12.3 fetch_pool を改造する

Ch.5 の fetch_pool は次のような SQL でした: 

SELECT character_id, weight
  FROM gacha_items
 WHERE gacha_id = %s;

ここに「アクティブな pickup_periods が character_id を盛っているなら weight を倍率倍する」 を足します。 LEFT JOIN LATERAL + JSONB のキャストで書けます: 

SELECT gi.character_id,
       gi.weight * COALESCE(p.mult, 1) AS weight
  FROM gacha_items gi
  LEFT JOIN LATERAL (
        SELECT (pp.weights ->> gi.character_id::text)::numeric AS mult
          FROM pickup_periods pp
         WHERE pp.gacha_id = gi.gacha_id
           AND NOW() <@ pp.period
           AND pp.weights ? gi.character_id::text
         LIMIT 1
       ) p ON TRUE
 WHERE gi.gacha_id = %s;

SQL の読み方

  • NOW() <@ pp.period ← 現在時刻が期間に含まれるか。 GIST インデックスが効く。
  • pp.weights ? gi.character_id::text ← JSONB に「そのキャラのキー」 があるか。 ? は JSONB の存在演算子。
  • weights ->> gi.character_id::text ← JSONB から値を テキストとして取り出す。 -> だと JSON 値 (数値型のままだが扱いにくい)、 ->> はテキスト。 ::numeric でちゃんと数値に戻す。
  • LATERAL + LIMIT 1 ← 同じガチャに重複して期間が走っていても 1 行だけ拾う。 実運用では「同時並行ピックアップがあったら倍率を掛け算」 なら SUM や EXP(SUM(LN(...))) に変える等、 サービス方針による。
  • COALESCE(p.mult, 1) ← 期間ヒットなしのキャラはそのまま 1 倍。

12.4 Python 側の変更は実は最小

抽選ロジック本体 (重み付き乱択) は一切変えません。 SQL が返す weight が 期間中だけ大きくなるだけ。 ガチャを引く Python 側はその weight を使うだけ: 

def fetch_pool(conn, gacha_id):
    with conn.cursor() as cur:
        cur.execute(
            """
            SELECT gi.character_id,
                   gi.weight * COALESCE(p.mult, 1) AS weight
              FROM gacha_items gi
              LEFT JOIN LATERAL (
                    SELECT (pp.weights ->> gi.character_id::text)::numeric AS mult
                      FROM pickup_periods pp
                     WHERE pp.gacha_id = gi.gacha_id
                       AND NOW() <@ pp.period
                       AND pp.weights ? gi.character_id::text
                     LIMIT 1
                   ) p ON TRUE
             WHERE gi.gacha_id = %s
            """,
            (gacha_id,),
        )
        return cur.fetchall()

API も変わらない — フロントは何も知らずに、 期間中だけ「ドラゴンが当たりやすいな」 と感じる。 これがマスタを触らない設計の旨み。

12.5 GIST インデックスの効果を観察する

実習 step5 で EXPLAIN ANALYZE を流して、 GIST インデックスがあるとき / 無いときで 実行計画と実行時間を比較します。 pickup_periods が数万行に育つ前提だと、 GIST 無しではガチャ 1 回の fetch_pool が秒単位かかるくらい遅くなります。

12.6 期間切れの後

期間が過ぎた行を消す必要は基本ありません。 NOW() <@ pp.period で勝手にヒットしなくなる。 残しておけば「先月の GW にどんなピックアップを走らせたか」 の運用ログにもなる。 容量がきつくなってきたら、 半年経った行を月次バッチで DELETE WHERE upper(period) < NOW() - INTERVAL '6 months' する程度。

12.7 落とし穴まとめ

  • マスタ (gacha_items.weight) は絶対に書き換えない
  • 範囲型のクエリには GIST インデックスが必須
  • JSONB の値取り出しは ->> + ::numeric で型を戻す
  • 同時並行ピックアップの扱い (掛け算 / 加算 / 1 件採用) はサービス方針として明文化する
