第 6 章 — Box と JOIN・集計

Ch.5 でガチャを引けるようになりました。 引いた履歴は user_characters テーブルに溜まっていきますが、 フロントの「Box」 画面はまだハードコード (毎回ドラゴン 1 体) のまま。 この章で履歴から「所持品一覧 + 個数」 を集計 して返す本実装をやります。

3 ステップで:

  1. JOIN で履歴とキャラマスタを 1 枚に
  2. GROUP BY + COUNT で同じキャラを 1 行に圧縮
  3. /api/box ハンドラを書いて、 通算引いた回数 (total_pulls) も返す

6.1 JOIN: 履歴とマスタを 1 枚に

user_characters テーブルには character_id しか入っていません。 これだけでは「何のキャラを持っているか」 が分からないので、 characters マスタと結合して キャラ名 / レア度 / 絵文字をくっつけます。

📚 コラム: JOIN と「結合キー」

JOIN = 2 つのテーブルを同じ値の列で繋いで横に並べる操作。 繋ぐ基準になる列を「結合キー」 と呼びます。

主に 4 種類:

  • INNER JOIN (JOIN のみ): 両方のテーブルにマッチした行だけ残す。 一番よく使う
  • LEFT JOIN: 左のテーブルは全行残す、 右にマッチがなければ NULL。 「未所持を含む全キャラ一覧」 を出す等に
  • RIGHT JOIN: LEFT の逆。 実務では LEFT を反転して書く方が多いので使われない
  • FULL OUTER JOIN: 両方の全行を残す。 これも実務では稀

本教材では INNER JOIN と LEFT JOIN だけ知っておけば十分。

📒 SQL の前提知識: テーブルエイリアス と JOIN ... ON 構文

これから出てくるクエリには uc、 c といった謎の短い名前が出てきます。 これは テーブルエイリアス(別名)で、 長いテーブル名を毎回書かずに済ませるためのもの。 まず仕組みを 1 つずつ整理します。

(1) テーブルエイリアス: FROM user_characters uc

FROM や JOIN の後にスペース 1 つ空けて短い名前を書くと、 そのテーブルを その名前で呼べるようになります。 

FROM user_characters AS uc      -- 正式: AS uc で「uc という名前で扱う」
FROM user_characters    uc      -- AS は省略可。 同じ意味
FROM user_characters            -- エイリアスなしだとそのまま user_characters.* で参照する

本教材を含め多くのスタイルでは AS は省略します。 これだけ:

SELECT uc.id, uc.user_id, c.name      -- ↓ ここに対応
  FROM user_characters uc             -- uc = user_characters の別名
  JOIN characters       c             -- c  = characters       の別名
    ON c.id = uc.character_id

なぜエイリアスを付けるのか:

  • 列名の曖昧さを避ける: id という列名は両方のテーブルにある。 uc.id / c.id と書けば「どっちのテーブルの id か」 を明示できる
  • タイプ量を減らす: user_characters.character_id より uc.character_id の方が短い
  • 同じテーブルを 2 回使うときに必須: 例えば「友達と自分の Box を比較」 のように、 1 つの SQL で同じテーブルを 2 回 JOIN するときは、 違うエイリアスを付けないと区別できない

(2) JOIN ... ON の構文

FROM <左テーブル> <エイリアス>
JOIN <右テーブル> <エイリアス>
  ON <結合条件>

結合条件 (ON ...) には「どの列とどの列の値が等しい行どうしをくっつけるか」 を書きます。 99% は 外部キー = 主キー の形: 

  FROM user_characters uc
  JOIN characters       c
    ON c.id = uc.character_id
--     ^^^^   ^^^^^^^^^^^^^^^^^
--     c の主キー = uc の外部キー
--     (履歴側の「キャラ ID 票」 で、 マスタ側のドラゴン情報を引っ張ってくる)

この 1 行で DB は「uc.character_id と等しい c.id を探して、 その行を横に連結する」 という処理を全行に対してやってくれる。

📚 コラム: SQL の JOIN を Kotlin/Java で書くと?

実は同じことを Kotlin の HashMap 引きで書ける: 

// characters マスタを id でひける Map にしておく
val byId: Map<Long, Character> = characters.associateBy { it.id }

// 履歴を回しながら、 マスタを引く (= JOIN)
for (uc in user_characters) {
    val c = byId[uc.character_id]   // ← これが ON c.id = uc.character_id
    println("${c.name} を ${uc.obtained_at} に取得")
}

SQL の JOIN はこれを DB に肩代わりしてもらう記法。 ループも HashMap も書かず、 「結合キー」 を宣言するだけで、 DB 側が量に応じて最適なアルゴリズム(Hash Join、 Nested Loop、 Merge Join 等)を 自動で選んでくれる。 件数が多いほど SQL の方が圧倒的に速い。

動作確認: SQL で先に試す

📒 セル 6-A — JOIN だけしてみる 
-- psql で直接打って試す
-- guest (id=1) の履歴 + キャラ情報
SELECT uc.id AS uc_id,        -- uc_id という別名で出力
       c.name, c.rarity, c.emoji, uc.obtained_at
  FROM user_characters uc      -- 履歴テーブル(uc という別名)
  JOIN characters       c      -- キャラマスタ(c という別名)
    ON c.id = uc.character_id  -- 結合条件: 履歴の character_id でマスタを引く
 WHERE uc.user_id = 1          -- guest の行だけ
 ORDER BY uc.id;

Ch.5 でガチャを引いていれば、 引いた回数ぶんの行が出ます。 同じキャラを 2 回引いていれば 2 行 出る (= 履歴なので重複を許す)。 これを 1 行にまとめるのが次のステップ。

📚 コラム: SELECT uc.id AS uc_id の AS は何?

列にも別名が付けられます。 これがあるのは「2 つのテーブルから同じ列名 (id) を SELECT したい」 とき: 

SELECT uc.id, c.id        -- ❌ 結果テーブルに "id" 列が 2 つ → アクセスしづらい
SELECT uc.id AS uc_id,
       c.id  AS char_id   -- ✅ uc_id / char_id と別名で出力

Python 側で row["uc_id"] として受け取るときに役立つ。 Ch.5 の fetch_pool で SELECT c.id AS character_id としていたのも、 dataclass の character_id フィールドに合わせるためのリネーム。 SQL を変える時はこの「列名契約」 を意識すると壊しにくい。

6.2 GROUP BY + COUNT で「個数別」 にまとめる

6.1 のクエリは履歴行を 1 行ずつ展開するだけでした。 同じスライムを 3 回引いていれば、 結果も 3 行のスライムが並ぶ。 でも Box の見せ方としては 「スライム ×3」 のように 1 行にまとめたい。 そのための仕組みが GROUP BY。

具体例: 5 回引いた履歴を 「Box」 表示に圧縮する

例えばユーザー (id=1) が 5 回引いて、 6.1 の JOIN クエリの結果がこうだったとします: 

(GROUP BY する前)
 uc.id | c.id | c.name   | c.rarity | uc.obtained_at
-------+------+----------+----------+------------------
   1   |   1  | スライム |    1     | 14:30
   2   |   1  | スライム |    1     | 14:35     ← 同じスライムが 2 回目
   3   |  10  | ドラゴン |    5     | 14:40
   4   |   1  | スライム |    1     | 14:42     ← 同じスライムが 3 回目
   5   |   2  | コウモリ |    1     | 14:45

ここに GROUP BY c.id を付けると、 c.id が同じ行どうしを 1 つの "グループ" にまとめ、 各グループに対して 1 行ずつ 集計値が出ます: 

(GROUP BY c.id した後)
 c.id | c.name   | c.rarity | COUNT(*) | MIN(obtained_at) | MAX(obtained_at)
------+----------+----------+----------+------------------+------------------
   1  | スライム |    1     |    3     | 14:30            | 14:42
   2  | コウモリ |    1     |    1     | 14:45            | 14:45
  10  | ドラゴン |    5     |    1     | 14:40            | 14:40

これで「スライム × 3 / コウモリ × 1 / ドラゴン × 1」 が一目でわかる Box ができた。 MIN(obtained_at) は「初めて引いた時刻」、 MAX(obtained_at) は「最後に引いた時刻」。

📚 コラム: 集計関数と GROUP BY

集計関数 = 「複数行 → 1 値」 への圧縮器。 グループの中の行を全部見て、 1 つのスカラ値を返す。 SQL で頻出するのは:

  • COUNT(*) — 行数。 COUNT(列) ならNULL を除いた非 NULL 値の数
  • SUM(列) — 数値列の合計
  • AVG(列) — 数値列の平均
  • MIN(列), MAX(列) — 最小・最大。 日時にも文字列にも使える

集計関数を GROUP BY なしで 使うと、 テーブル全体に対する 1 値が出る: SELECT COUNT(*) FROM user_characters → 全行数。

GROUP BY 列 を付けると、 その列ごとにグループ分けして、 各グループに対して 1 行ずつ集計値が出る。

📌 GROUP BY 列の選び方ルール

SQL の標準ルールでは、 GROUP BY を付けたとき、 SELECT に書ける列は 次の 2 種類だけ:

  1. GROUP BY に書いた列そのもの(各グループで値が一意に決まる)
  2. 集計関数を通した列(COUNT(*)、 MIN(...) など)

例えば SELECT c.name FROM ... GROUP BY c.id は本来エラー。 「c.name はグループ内で一意か?」 が SQL からは保証できないため。

ただし PostgreSQL は賢くて、 GROUP BY 主キー をしているなら、 同じテーブルの他の列も自動的に一意 と認識してくれる(関数従属性の検出)。 だから本教材の SQL は GROUP BY c.id だけで動きます。

他の DB (MySQL の strict モードなど) や移植性を意識する場合は、 SELECT した非集計列を全部 GROUP BY に書く流派もある: 

-- 「c.id だけで GROUP BY」 (PostgreSQL ならこれで OK)
GROUP BY c.id

-- 「全部書く」 (どの DB でも動く保守的な書き方)
GROUP BY c.id, c.name, c.rarity, c.emoji

結果は両方同じ。 本教材の server/app.py 完成版は前者(短い方)、 教材の途中の例では 練習として後者(全部書く方)を見せるところもある。

📒 セル 6-B — GROUP BY で集計 + JOIN でキャラ名も付ける 
-- psql で直接打って試す
SELECT c.id, c.name, c.rarity, c.emoji,
       COUNT(*)            AS count,                -- 引いた回数
       MIN(uc.obtained_at) AS first_obtained_at,    -- 初めて引いた時刻
       MAX(uc.obtained_at) AS last_obtained_at      -- 最後に引いた時刻
  FROM user_characters uc
  JOIN characters       c ON c.id = uc.character_id
 WHERE uc.user_id = 1
 GROUP BY c.id, c.name, c.rarity, c.emoji           -- ← 保守的に全部書く流派
 ORDER BY c.rarity DESC, c.id;                       -- 高レアから順に

実行すると、 上の「具体例」 で示した形の表が出る。 MIN / MAX も同じ GROUP BY の中で取れるので、 「初めて獲得した日時」 「最後に獲得した日時」 も 1 つのクエリで返せます。

6.3 /api/box ハンドラを書く

フロントが期待する shape:

{
  "user":        { "id": 1, "name": "guest", "display_name": "ゲスト", "coins": 700 },
  "total_pulls": 3,
  "items": [
    { "id": 10, "name": "ドラゴン", "rarity": 5, "emoji": "🐉", "count": 1, ... },
    ...
  ]
}

集計クエリ + 通算引いた回数 (total_pulls) + ユーザー情報 を 1 ハンドラで束ねます。

📒 セル 6-C — /api/box の本実装 
@route("GET", "/api/box")
def box(h):
    user_id = 1   # まだ認証無し。 全員 guest として扱う

    with get_conn() as conn:
        # 1) 集計済みの所持キャラ一覧
        rows = conn.execute(
            """
            SELECT c.id, c.name, c.rarity, c.emoji,
                   COUNT(*)            AS count,
                   MIN(uc.obtained_at) AS first_obtained_at,
                   MAX(uc.obtained_at) AS last_obtained_at
              FROM user_characters uc
              JOIN characters       c ON c.id = uc.character_id
             WHERE uc.user_id = %s
             GROUP BY c.id
             ORDER BY c.rarity DESC, c.id
            """,
            (user_id,),
        ).fetchall()

        # 2) 通算 pull 回数 (= 履歴の総数)
        total_pulls = conn.execute(
            "SELECT COUNT(*) AS n FROM user_characters WHERE user_id = %s",
            (user_id,),
        ).fetchone()["n"]

        # 3) 最新の coins / ユーザー情報
        u = dict(conn.execute(
            "SELECT id, name, display_name, coins FROM users WHERE id = %s",
            (user_id,),
        ).fetchone())

    h._json(200, {
        "user":        u,
        "total_pulls": total_pulls,
        "items":       [dict(r) for r in rows],
    })

print("✅ /api/box が実 DB の集計を返すように")

🧪 動作確認

  1. フロント (ガチャ画面) で「最新化」 ボタン (Box の右上)
  2. Ch.5 で引いた分のキャラが Box に並ぶ
  3. レア度の高い順に並ぶ (= ORDER BY c.rarity DESC が効いている)
  4. 同じキャラを 2 回引くと、 右上に ×2 バッジが表示される
  5. 下部のサマリ: 「N 回引いた / M 種類」 が表示される

コインも Ch.5 の pull で更新された値が見える。 ガチャ → DB → Box の流れがぜんぶ繋がっています。

6.4 ここまでで気づくこと — 次章への動機

ここまでで「ガチャを引く」 「Box に蓄積される」 が動いています。 でも仕組みをよく見ると気になる点があります。

🤔 ちょっと待って
  • 誰がアクセスしても、 全員が「guest」 として同じ Box を覗く状態
  • 友達と一緒に遊ぶ場合、 自分が引いたキャラを友達が見られるし、 友達のコインを自分が使えてしまう
  • そもそもログイン画面が機能してない (Ch.4 末で /api/me が常に guest を返す)

これだと「俺のドラゴン」 「私のスライム」 が成立しない。 せっかく集めたのに自分のものにならない。

ここまで「ガチャを引いて Box に集める」 という遊びの部分は出来た。 でもこれを本当の意味で「自分の」 ものにするには、 個別ユーザーの概念が必要です。 そのために次章ではユーザー登録 / ログイン / セッション管理を導入します。

  • 「未所持の SSR (rarity=5) のみ」 を返す API /api/box/missing を追加してみよう — ヒント: LEFT JOIN ... WHERE uc.id IS NULL
  • 「レア度別のコンプリート率」 を返す API。 characters 全体に対して所持しているキャラの割合
  • これらを実装して、 フロントから叩いて結果を見る (デバッグコンソールで確認)

本章のまとめ

  • JOIN: 同じ値の列でテーブルを横に繋げる。 INNER JOIN がメイン、 LEFT JOIN は補助
  • GROUP BY: 列の値ごとにグループ分け。 各グループに集計関数を適用
  • 集計関数: COUNT/SUM/AVG/MIN/MAX。 MIN/MAX は数値だけでなく日時にも使える
  • 履歴テーブル + 集計クエリ = 「現在の状態」 を引き出す王道パターン
  • でも全員 guest 共有はおかしい → 次章でユーザー管理を導入する動機が見えた
