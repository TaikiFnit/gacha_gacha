第 10 章 — ログインボーナス (デイリー報酬)

Ch.9 では「拡張アイディア」 として軽く紹介した ログインボーナスを、 ここから本格的な章として組み上げていきます。 ガチャを長く遊ばせる定番機能であり、 同時に 「並行性をどう DB で守るか」を体で覚えるのにちょうど良い題材です。

🎯 この章のゴール
  1. POST /api/daily/claim を叩くと 200 coin もらえる
  2. 同じ日に二回叩くと 400 で弾かれる
  3. 同時に 2 リクエスト来てもどちらか片方しか通らない (DB が物理的に保証)

実習は exercises/ch10/ に step1〜step6 として置いてあります。 step を上から順に実行していくと、 そのままこの章のゴールが手元に組み上がります。 本物の server/app.py はいじりません — exercises 配下だけで完結します。

10.1 何を作るか

実装するエンドポイントは 1 つだけ: 

POST /api/daily/claim
  → 200 {"amount": 200, "claimed_on": "2026-04-28", "coins": 1200}
  → 400 {"error": "今日のボーナスはもう受け取り済みです"}  (2 回目)

シンプルに見えますが、 「同じ日に 2 回叩いたら 400」を素朴に 実装すると TOCTTOU (Time-Of-Check-To-Time-Of-Use) というバグを踏みます。 Ch.10 ではまず素朴版を書いて壊し、 そのあと UNIQUE 制約で物理的に塞ぐ流れで進めます。

10.2 テーブル設計

1 ユーザーが 1 日に 1 回だけ受け取れる、 を表現するには「ユーザー ID + 受取日」 を UNIQUE キーにしたテーブルが一番素直です。 

CREATE TABLE daily_bonuses (
    id          BIGSERIAL    PRIMARY KEY,
    user_id     BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    claimed_on  DATE         NOT NULL DEFAULT (CURRENT_DATE AT TIME ZONE 'Asia/Tokyo')::date,
    amount      INTEGER      NOT NULL,
    UNIQUE (user_id, claimed_on)
);

設計のポイント

  • UNIQUE (user_id, claimed_on) ← これが心臓部。 アプリが何回 INSERT してきても、 DB が物理的に 1 行しか入れさせない。
  • DEFAULT (CURRENT_DATE AT TIME ZONE 'Asia/Tokyo')::date ← サーバの timezone がどうであれ「日本時間で日付が変わったら新しい行」 になるよう DB 側で日付を確定させる。 アプリ言語側で日付を作って渡すと、 サーバの TZ 設定に 引きずられて事故るので注意。
  • ON DELETE CASCADE ← ユーザー削除時にもらった履歴も消える。 履歴を残すなら ON DELETE SET NULL + user_id NULL 可 に 変えてもよい (ここはサービス方針)。

10.3 素朴な実装 (まず壊す)

最初に「素朴版」 を書きます。 「今日のレコードある? を SELECT で確認して、 無ければ INSERT」 という、 一見正しそうなパターン: 

@route("POST", "/api/daily/claim")
def claim_daily_naive(h):
    AMOUNT = 200
    with get_conn() as conn:
        user = h.require_user(conn)
        with conn.cursor() as cur:
            # 1. 今日の行があるか確認
            cur.execute(
                "SELECT 1 FROM daily_bonuses "
                "WHERE user_id = %s "
                "  AND claimed_on = (CURRENT_DATE AT TIME ZONE 'Asia/Tokyo')::date",
                (user["id"],),
            )
            if cur.fetchone() is not None:
                raise bad_request("今日のボーナスはもう受け取り済みです")

            # 2. 無ければ INSERT
            cur.execute(
                "INSERT INTO daily_bonuses (user_id, amount) VALUES (%s, %s)",
                (user["id"], AMOUNT),
            )
            cur.execute(
                "UPDATE users SET coins = coins + %s WHERE id = %s "
                "RETURNING coins",
                (AMOUNT, user["id"]),
            )
            new_coins = cur.fetchone()["coins"]
    h._json(200, {"amount": AMOUNT, "coins": new_coins})

この実装は 1 リクエストずつ来る分には正しく動きます。 でも、 ほぼ同時に 2 リクエストが 来たときに 両方とも SELECT で「行が無い」 と判定して、 両方 INSERT が通ってしまう。 これが TOCTTOU バグです。

⚠️ TOCTTOU の本質

「チェック (Time-Of-Check)」 と「使用 (Time-Of-Use)」 の間に、 他のトランザクションが状態を変えてしまえる、 という穴。 単一プロセス・単一スレッドで動いている間は表面化しないが、 本番環境では必ず起きる。

10.4 UNIQUE 制約で物理的に塞ぐ

正解は「 SELECT で確認する前に INSERT しちゃう」です。 UNIQUE 制約があるので、 二重投入なら DB 側が UniqueViolation エラーで弾いてくれる。 アプリ側はそれを 400 に翻訳するだけ。 

import psycopg

@route("POST", "/api/daily/claim")
def claim_daily(h):
    AMOUNT = 200
    with get_conn() as conn:
        user = h.require_user(conn)
        with conn.cursor() as cur:
            try:
                cur.execute(
                    """
                    INSERT INTO daily_bonuses (user_id, amount) VALUES (%s, %s)
                    RETURNING claimed_on
                    """,
                    (user["id"], AMOUNT),
                )
                claimed_on = cur.fetchone()["claimed_on"]
            except psycopg.errors.UniqueViolation:
                raise bad_request("今日のボーナスはもう受け取り済みです")

            cur.execute(
                "UPDATE users SET coins = coins + %s WHERE id = %s "
                "RETURNING coins",
                (AMOUNT, user["id"]),
            )
            new_coins = cur.fetchone()["coins"]
    h._json(200, {
        "amount": AMOUNT,
        "claimed_on": claimed_on,
        "coins": new_coins,
    })

ポイントは 3 つ:

  • INSERT 一発。 二重チェックを書かない。
  • UniqueViolation を bad_request (= 400) に変換するのは アプリ層の責務。 DB のエラーをそのままユーザーに返さない。
  • INSERT と UPDATE は同じ with get_conn() ブロック内= 同一トランザクション。 片方だけ成功するのを防ぐ。

10.5 並行性を実機で確認する

理屈で「TOCTTOU が塞がっている」 と言われても、 本当に 2 リクエスト同時に来たときに 片方だけ通るのか、 自分の目で見ないと信じきれません。 exercises/ch10/step4_concurrent_test.py を使って 2 つのリクエストを同時に投げ、 片方が 200, もう片方が 400 になるのを確認します。 

import threading, urllib.request, json

URL = "http://127.0.0.1:8001/api/daily/claim"
TOKEN = "..."  # ログイン済みトークン

results = []

def fire():
    req = urllib.request.Request(
        URL, method="POST",
        headers={"Authorization": f"Bearer {TOKEN}"},
    )
    try:
        with urllib.request.urlopen(req) as r:
            results.append((r.status, r.read().decode()))
    except urllib.error.HTTPError as e:
        results.append((e.code, e.read().decode()))

threads = [threading.Thread(target=fire) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()

print(results)
# 期待: [(200, '...amount...'), (400, '...受け取り済み...')] の順不同

http.server は 1 リクエストずつ処理するので、 完全な並行性を観察するには ThreadingHTTPServer に切り替える必要があります。 step4 ではそこも切り替え 済みのコードを置いているので、 そのまま動かせばよいです。

10.6 タイムゾーンの境界

「日付が変わる瞬間」はバグの宝庫です。 サーバを UTC で動かしている場合、 日本時間 0 時から 9 時までの間に受け取ると、 サーバから見ると「まだ前日」 で、 claimed_on が前日の日付で入ります。 これだと「日本時間で 0 時を回ったら 新しいボーナスをもらえる」 という体験にズレます。

対策はテーブル定義の DEFAULT (CURRENT_DATE AT TIME ZONE 'Asia/Tokyo')::date で日本時間に正規化していることに尽きます。 日付の決定は DB 側に寄せるのが 鉄則 — アプリ言語側で datetime.today().date() を作って渡すと、 アプリのプロセスが UTC で動いていれば UTC 日付になってしまう。

📝 演習

step5 では PG の SET TIME ZONE 'UTC' で接続を UTC に切り替えてから INSERT してみる演習があります。 DEFAULT に AT TIME ZONE を書いた効果が 消えないことを観察します。

10.7 落とし穴まとめ

  • 素朴な「SELECT してから INSERT」 は必ず TOCTTOU バグを抱える
  • 正解は「INSERT を投げて UNIQUE 違反をキャッチ」 — DB に物理保証してもらう
  • INSERT と UPDATE は同じトランザクションに置く
  • 日付の確定はサーバ側ではなくDB 側 (AT TIME ZONE) で
  • 並行性は理屈ではなく実機で観察する (step4)
