第 14 章 — マイグレーション (本番のスキーマ更新)

ここまで本教材では、 db/schema.sql を 1 回流せばスキーマが整う前提で来ました。 でも本番運用では「既存データを残しながら」テーブルや列を増やす必要があります。 それを支える仕組みがマイグレーション。 自前で番号順 SQL ランナーを組み、 概念を 体で理解します。

🎯 この章のゴール
  1. db/migrations/0001_initial.sql, 0002_*.sql ... と番号順 SQL を運用する
  2. 適用済みファイル名を記録する schema_migrations テーブル
  3. 未適用分だけ流すランナースクリプト scripts/ch14_migrate.py
  4. 「列追加 (default 付き) → アプリ更新 → 制約強化」 の段階デプロイを実演
📝 本物の db/ は触らない

本教材の db/init.sql は Ch.1〜8 のための既存資産です。 Ch.14 の演習は exercises/ch14/ 配下に migrations/ を切って、 本物の db/ と独立に試します。 本物の運用に取り入れるのは Ch.14 を理解してからで OK。

14.1 何を解決したいのか

開発中は docker compose down -v で全部消して schema.sql を再投入すれば 「常に最新状態」 を保てる。 でも本番では:

  • 既存ユーザーのデータを消したら終わり
  • 「列を追加したい」 程度の変更が日常的に発生する
  • 複数人で開発するなら「誰がどの順で適用したか」 を一致させる必要がある

解は 「変更を 1 ステップ = 1 ファイル に切り、 番号順に流す」。 適用済みファイルは記録して、 同じファイルは 2 回流さない。 これだけ。

14.2 schema_migrations テーブル

CREATE TABLE IF NOT EXISTS schema_migrations (
    filename    TEXT        PRIMARY KEY,
    applied_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

これが「DB 自身が記憶する適用ログ」。 filename が PK なので 2 回 INSERT は弾かれる。 ランナーはこのテーブルを見て「未適用のファイル」 だけ流す。

14.3 マイグレーションファイルの書き方

ファイル名は NNNN_*.sql (4 桁ゼロ埋め + 説明)。 ファイル名自体に 適用順が組み込まれていれば sorted() で並べ替え可能。 

db/migrations/
├── 0001_initial.sql            ← 既存 schema.sql を貼り付け
├── 0002_daily_bonuses.sql      ← Ch.10 で追加した分
├── 0003_idle_coins.sql         ← Ch.11 で追加した分
├── 0004_pickup_periods.sql     ← Ch.12 で追加した分
├── 0005_friendships.sql        ← Ch.13 で追加した分
└── 0006_users_public_box.sql   ← Ch.13 で追加した分

各ファイルは「単一トランザクションで意味のあるかたまり」 にする。 1 ファイルが大きすぎると失敗時のリカバリが辛いので、 1 機能 1 ファイル くらいの粒度で切るのがコツ。

14.4 ランナースクリプト

"""scripts/ch14_migrate.py — 未適用の SQL を順に流す最小ランナー。"""
import os, pathlib, sys
import psycopg

MIGRATIONS_DIR = pathlib.Path(__file__).resolve().parents[1] / "db" / "migrations"

def main():
    dsn = os.environ.get("DATABASE_URL", "host=127.0.0.1 user=gacha password=gacha dbname=gacha")
    with psycopg.connect(dsn, autocommit=False) as conn:
        with conn.cursor() as cur:
            cur.execute(
                "CREATE TABLE IF NOT EXISTS schema_migrations ("
                "  filename   TEXT PRIMARY KEY,"
                "  applied_at TIMESTAMPTZ NOT NULL DEFAULT NOW()"
                ")"
            )
            cur.execute("SELECT filename FROM schema_migrations")
            applied = {row[0] for row in cur.fetchall()}

        files = sorted(p.name for p in MIGRATIONS_DIR.glob("*.sql"))
        pending = [f for f in files if f not in applied]
        if not pending:
            print("up to date.")
            return

        for name in pending:
            path = MIGRATIONS_DIR / name
            print(f"applying {name} ...")
            sql = path.read_text(encoding="utf-8")
            try:
                with conn.cursor() as cur:
                    cur.execute(sql)
                    cur.execute(
                        "INSERT INTO schema_migrations (filename) VALUES (%s)",
                        (name,),
                    )
                conn.commit()
                print(f"  ok")
            except Exception as e:
                conn.rollback()
                print(f"  FAILED: {e}", file=sys.stderr)
                sys.exit(1)

if __name__ == "__main__":
    main()

ポイント:

  • 1 ファイル = 1 トランザクション で適用。 失敗したらその 1 ファイル分だけロールバック。 次回はそこから再開できる。
  • schema_migrations への INSERT を同じトランザクションに 含めるのが大事。 「SQL は通ったが INSERT 前に死んだ」 だと次回二重実行される。
  • ファイル並び替えはファイル名の文字列順。 番号 4 桁ゼロ埋めは 9999 件まで衝突しないので十分。

14.5 段階デプロイ — 列追加で本番を壊さないコツ

「users に email 列を追加して、 NOT NULL にしたい」。 これを 1 ファイルでやろうとすると: 

-- BAD: 既存行に email が無いので NOT NULL を即適用するとエラー
ALTER TABLE users ADD COLUMN email TEXT NOT NULL;

正解は3 段階に分ける: 

-- 0007_users_email_step1.sql  (default 付きで列追加)
ALTER TABLE users ADD COLUMN email TEXT NOT NULL DEFAULT '';
-- 0008_users_email_step2.sql  (アプリ更新後、 既存行に値を埋める)
UPDATE users SET email = name || '@example.com' WHERE email = '';
-- 0009_users_email_step3.sql  (default 削除 + UNIQUE 化)
ALTER TABLE users ALTER COLUMN email DROP DEFAULT;
ALTER TABLE users ADD CONSTRAINT users_email_unique UNIQUE (email);

間にアプリのリリースを挟む — step1 でアプリを更新し、 新規登録は まともな email を書き込むようにしてから、 step2 で過去の空文字をマイグレートし、 step3 で制約を強化する。 これが運用での「壊さない」 鉄則。

⚠️ 「危険な変更」 は本番でロックを長く取る

大きなテーブルへの ALTER TABLE ADD COLUMN ... DEFAULT '...' は PostgreSQL 11 以降は高速化されたが、 UPDATE で全行書き換えは テーブル全体の書き込みロックを取る。 メンテナンスウィンドウを取るか、 バッチで小分けに UPDATE するのが安全。

14.6 ロールバックの考え方

自前ランナーには「down マイグレーション」 (取り消し SQL) を作る場合と作らない場合があります。 実運用は「失敗したら次の番号で打ち消す」方が安全 — 過去の番号を書き換えると 他の環境との同期がズレるので。 

db/migrations/
├── 0007_add_evil_column.sql      ← 失敗したマイグレーション
└── 0008_revert_evil_column.sql   ← 0007 を打ち消す DROP COLUMN

履歴は残す、 状態は前進する。 これが番号付き SQL ランナーの一番素直な使い方です。

14.7 既存ツールへの橋渡し

  • Alembic (SQLAlchemy 系。 Python 製。 自動生成も可能)
  • golang-migrate (Go 製。 純 SQL を読み込む。 言語非依存に近い)
  • Flyway (Java 系。 番号付き SQL の文化はここがルーツ)

この章で書いた最小ランナーを理解してから既存ツールを触ると、 「あぁ、 同じこと細かく やっているだけ」と透けて見えます。

14.8 落とし穴まとめ

  • 1 ファイル = 1 トランザクション、 schema_migrations への INSERT も同じ TX に
  • 過去の番号は絶対に書き換えない。 失敗したら次の番号で打ち消す
  • NOT NULL を後付けするときは「default → backfill → drop default + add unique」 の 3 段階
  • ロックの長い ALTER は本番でメンテナンスウィンドウを取る
