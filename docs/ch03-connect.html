第 3 章 — Python から DB を叩く

Ch.1 で HTTP サーバ、 Ch.2 で users テーブルを作りました。 それぞれ別々に動かせるけど、 まだ繋がっていない。 この章で初めて 1 つのシステムになります。

ゴールはシンプル。 Bruno からサーバに POST してユーザーを 1 件作り、 ブラウザ (もしくは Bruno) でサーバの GET を叩くと DB に保存されたユーザーが JSON で返ってくる。 この 1 往復が成立した瞬間が、 本教材で最初に「自分で全部つないで動かした」 状態です。

📐 この章で学ぶこと

  • psycopg で Python から PostgreSQL に接続する
  • myserver.py に DB 呼び出しを足して、 INSERT / SELECT を発行する
  • Bruno で POST、 ブラウザで GET を試して動くものを確かめる
📝 まだ扱わないこと

  • SQL インジェクション対策 (%s プレースホルダは使うが、 「なぜ」 の話は Ch.5)
  • JOIN / GROUP BY / トランザクション (必要になる Ch.5 / Ch.6 で)

3.1 これから作るシステム

Ch.4 以降ではこの構成のまま規模を大きくしていきます。 Bruno はブラウザのフロント (web/) になり、 サーバは認証や抽選など本気の処理を持つようになります。 でも骨格はこれと同じ。

3.2 Python の仮想環境 (venv) を作る

Ch.0 でグローバルにインストールした Python に、 教材で使うライブラリをそのまま入れていくのは 非推奨です。 別のプロジェクトで違うバージョンが必要になったとき競合するため、 普通はプロジェクトごとに「仮想環境 (venv)」 を作って分離します。

▶️ venv を作る (PowerShell) 
cd $HOME\gacha_workspace

# .venv という名前で仮想環境を作る
python -m venv .venv

# その仮想環境を有効化
.\.venv\Scripts\Activate.ps1
# プロンプトの先頭に (.venv) が付けば成功

# pip と Python のパスを確認 (.venv の中を指していること)
where.exe python
pip --version
⚠️ Activate.ps1 が「実行が許可されていません」 とエラーになる場合

PowerShell の実行ポリシーを 1 度だけ変える必要があります: 

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

その後、 もう一度 .\.venv\Scripts\Activate.ps1 を実行してください。 無効化するには deactivate と打つだけです。

psycopg をインストール

Postgres の Python ドライバ psycopg (バージョン 3 系) をインストールします。 [binary] を付けるとプリビルド済みのバイナリ版が入って、 C ヘッダのコンパイルが要らなくなります。

▶️ pip install 
# venv を有効化した状態で
pip install "psycopg[binary]"

# 確認
python -c "import psycopg; print(psycopg.__version__)"
✅ 期待される出力 
3.x.x

仮想環境が無効化されると python や pip がグローバルなものに戻り、 psycopg が見つからなくなります。 PowerShell を開き直したら毎回 .\.venv\Scripts\Activate.ps1 を打つのを忘れずに。

📚 コラム: requirements.txt で依存を固定する

プロジェクトの依存パッケージをテキストファイルで宣言しておくと、 他の人 / 他の PC でも同じ環境を再現できます: 

# 現在 venv に入っているものを書き出す
pip freeze > requirements.txt

# 別 PC ではこれで一発復元
pip install -r requirements.txt

本教材では依存が psycopg[binary] しかないので、 requirements.txt は 実質 1 行です。 リポジトリには server/requirements.txt として既に置いてあります。

3.3 Python から PG に接続して SELECT

まずは myserver.py を触る前に、 独立したスクリプトで接続を試します。 接続できてようやく、 「サーバに組み込む」 価値が出てきます。

📝 db_check.py — 接続確認用スクリプト 
# db_check.py
# Postgres に接続して SELECT を 1 回打って、 結果を表示するだけ。
import psycopg
from psycopg.rows import dict_row

DSN = dict(
    host="localhost",
    port=5432,
    dbname="gacha",
    user="gacha",
    password="gacha",
)

with psycopg.connect(**DSN, row_factory=dict_row) as conn:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name, display_name FROM users ORDER BY id")
        for row in cur.fetchall():
            print(row)
▶️ 動かす 
# venv が有効化された状態で
python db_check.py
✅ 期待される出力 (Ch.2 で alice/bob を残していれば) 
{'id': 1, 'name': 'alice', 'display_name': 'アリス・スミス'}
{'id': 2, 'name': 'bob', 'display_name': 'ボブ'}

💡 解説

  • psycopg.connect(**DSN, ...) で Postgres と接続。 **DSN は dict をキーワード引数として展開する記法
  • row_factory=dict_row を指定すると、 結果の各行が tuple ではなく dict で返る。 後で JSON にするのに便利
  • with ブロックを抜けるときに自動で close される。 コネクションリーク防止
📚 コラム: なぜ psycopg は「3 系」 なのか

Postgres 用 Python ドライバには長らく psycopg2 という定番がありました。 2021 年に psycopg 3 がリリースされ、 こちらが新世代の定番になっています。 本教材では psycopg 3 を使います。 違いの主なポイント:

  • パッケージ名が psycopg2 → psycopg (= バージョンサフィックスなし)
  • 非同期 (asyncio) ネイティブ対応
  • row_factory が組み込み (dict_row, namedtuple_row, ...)
  • サーバサイド準備済みステートメントの自動管理

既存の Postgres + Python プロジェクトに psycopg2 を見たら、 「2 系」 だと判断してください (古いコードでは import psycopg2 となっています)。

3.4 myserver.py に DB 接続を組み込む

Ch.1 で書いた myserver.py に、 DB 接続用のヘルパと、 ユーザー操作の API を 2 つ追加します。 ステップ 6 の完成版を出発点にします。

📝 myserver.py — DB 接続ヘルパを追加

myserver.py の冒頭の import 群と、 ROUTES 定義の前のあたりに 以下を追記します: 

import psycopg
from psycopg.rows import dict_row
from contextlib import contextmanager

DB_PARAMS = dict(
    host="localhost",
    port=5432,
    dbname="gacha",
    user="gacha",
    password="gacha",
)

@contextmanager
def get_conn():
    """1 リクエストぶんの DB 接続を貸す。 ブロックを抜けるときに commit / rollback。"""
    conn = psycopg.connect(**DB_PARAMS, row_factory=dict_row)
    try:
        yield conn
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()
📝 myserver.py — POST /api/users と GET /api/users を追加

ROUTES 定義の中に、 既存のルートに加えて以下を追加します: 

@route("POST", "/api/users")
def create_user(h):
    body = h._read_json()
    name = (body.get("name") or "").strip()
    display_name = (body.get("display_name") or name).strip()
    if not name:
        raise bad_request("name は必須")

    with get_conn() as conn, conn.cursor() as cur:
        # %s はプレースホルダ。 文字列を直接埋め込まないこと (Ch.5 で詳しく)
        cur.execute(
            """
            INSERT INTO users (name, display_name)
            VALUES (%s, %s)
            RETURNING id, name, display_name, created_at
            """,
            (name, display_name),
        )
        row = cur.fetchone()
    h._json(200, {"user": row})


@route("GET", "/api/users")
def list_users(h):
    with get_conn() as conn, conn.cursor() as cur:
        cur.execute("SELECT id, name, display_name, created_at FROM users ORDER BY id")
        rows = cur.fetchall()
    h._json(200, {"users": rows})
📝 datetime と JSON

SELECT で返ってくる created_at は Python の datetime オブジェクトです。 標準 json.dumps はそのままでは datetime をシリアライズできません。 _json ヘルパに default=str を渡すよう書き換えます: 

def _json(self, status, obj):
    b = json.dumps(obj, ensure_ascii=False, default=str).encode("utf-8")
    #                                       ^^^^^^^^^^^^ ← これを足す
    self.send_response(status)
    self.send_header("Content-Type", "application/json; charset=utf-8")
    self.send_header("Content-Length", str(len(b)))
    self.end_headers()
    self.wfile.write(b)

default=str は「JSON にできない値が来たら str() で文字列化する」 の意味。 datetime は ISO 風の文字列になります。 これを忘れると、 GET /api/users が TypeError: Object of type datetime is not JSON serializable で 500 エラーになります。

3.6 ここまでで気づくこと

SQL を打つのと、 API 経由で見るのは別の経路

ブラウザで /api/users を見るのと、 psql で SELECT * FROM users を打つのと、 同じデータが見えました。 違いは:

  • API 経由: ネットワーク越し、 認証や絞り込みなどビジネスロジックを通る経路
  • SQL 直接 (psql): DB に直接アクセス。 開発者がデバッグや管理に使う経路

実運用では SQL 直接アクセスは「サーバ管理者だけ」 で、 一般ユーザーには API 経由しか触らせません。 しかし開発中はこの 2 つを両方見ることが、 動作を理解する一番の近道です。

「同じテーブル、 同じデータ」 を 2 つの世界が共有している

Ch.2 で psql から作ったテーブルに、 Ch.3 の Python コードが INSERT しました。 DB は共有資源。 サーバを止めても DB は残るし、 サーバを再起動しても以前のデータは見える。 これが永続化のありがたみ。
